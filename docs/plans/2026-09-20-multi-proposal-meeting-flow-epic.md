### 0.1 The tab story — central context for every per-tab grill (C32, C35)

The meeting flow **is** the in-home meeting, the proposal's creation and its presentation, in one place. Each tab is a chapter; the rep moves the customer from "who we are" to "let's build". Every tab gets its own deep grill later; this table is what each chapter is *for*, so a grill never re-litigates the story.

| # | Tab (label) | Step id (today → new) | Faces | What happens here | Per-tab grill |

## 4. Research findings (2026-09-20, read-only agents; spot-checked where marked ✔)

### 4.1 What "sent" means today

- **N1 ✔** Drafts are readable by token today: `getFullView` (`modules/proposals/core/dal/server/queries.ts:89`) has no status filter; the PDF and AI-summary routes have none either. Opening a draft by token also records a view and pushes "Proposal Viewed" to every participant + info@. Under a meeting token this becomes the main exposure → H4.
- **N2** `sendProposalEmail` (`proposals.router/delivery.router.ts:38-67`) has no server-side gate at all: it emails, then unconditionally writes `status: 'sent'` + `sentAt`, then calls `deriveOutcomeOnProposalSent`. Resend re-stamps `sentAt`; it also works server-side on an `approved` or `declined` proposal (only the UI hides the button; `status`/`sentAt` are outside `frozenProposalLockedFields`). P2's gate is a real gap, not a hypothetical.
- **N3** The emailed link is `ROOTS.public.proposalReview(proposalId, token)` = `/proposal-flow/proposal/{proposalId}?token=…` — one URL, one proposal, one token. Every homeowner action (finance option via generic update, `applyEnvelopeContext`, `requestToMoveForward`, PDF, AI summary) is keyed to that single `proposalId` → Q17.
- **N4 ✔** Meeting-level `hasSentProposal` is an equality check (`p.status = 'sent'`, `meetings/dal/server/queries.ts:180,293`), while the customer-level phone threshold uses `IN ('sent','approved')`. A meeting whose only sent proposal gets approved flips `hasSentProposal` back to false and re-disables the `proposal_sent` outcome option. More visible with several alternatives at different stages.
- **N5** Nothing touches sibling proposals when one is approved or signed — the "alternatives" model (C1) has no enforcement beyond the one-approved unique index → Q15.
- **N6** `deriveOutcomeOnProposalSent`, the phone-visibility threshold and the one-approved index are already meeting- or customer-scoped; they carry over unchanged. `features/proposal-flow/ui/views/proposal-view.tsx` is a dead stub (the live entry is `ui/components/proposal/index.tsx`).

### 4.2 Token blast radius (main)

- **T1 ✔ 🚨 present-day leak, independent of this epic:** `getFullView` selects `getTableColumns(proposals)` (`queries.ts:95-96`) and returns the whole row to a token holder — `projectJSON` with SOW `costLines` and section financials, `qbInvoiceId`, `qbPaymentStatus`. Agent-only data is hidden by the client-side `useViewMode` gate only; nothing is projected out server-side. Under a meeting token this multiplies across every alternative → H4 needs a server-side homeowner projection (also the natural home for P4's rep-private inputs).
- **T2** `shareableMiddleware` (`trpc/lib/middleware/shareable-middleware.ts:39-48`) builds a flat `eq(spec.tokenColumn, token)` on the spec's own table. The `parent: { spec, fk }` bridge (`shared/dal/server/lib/scope.ts:37-57`) is wired only into the session path (`resolveEffectiveScope`), never the token path. No structure option works with today's middleware — a token→meeting→proposals resolver is new work whichever shape wins.
- **T3** Three call sites bypass the middleware with a hand-rolled `proposal.token !== token` compare: `views/service.ts:57-66` (`recordView`), the PDF route (`app/api/proposals/[proposalId]/pdf/route.ts:12,24`), the AI-summary route (`…/summary/route.ts:16,33`). Each needs its own rewrite; one shared resolver should replace all three.
- **T4** Token-path WRITES today: generic `crud.update` (finance option), `fundingRouter.setCashInDeal`, `contractsRouter.applyEnvelopeContext` (customer age + envelope documents), `deliveryRouter.requestToMoveForward`, `viewsRouter.recordView`. All trust `ctx.scope` alone. With a meeting-wide scope a homeowner could write to alternatives they were never shown unless every write re-checks its target → H6.
- **T5** Meetingless proposals exist by design: `create.before` (`core/dal/server/crud.ts:29-32`) mints a token even with no `meetingId`, and `meetingId` is nullable with `onDelete: 'set null'` — deleting a meeting detaches its proposals from any meeting-owned token.
- **T6** `meetingId` is already in `frozenProposalLockedFields` (`proposal-lock.ts:69`): the lock ladder already blocks moving a locked proposal, so C12's "locked cannot move" is enforced for free.
- **T7** Link producers to re-source (H7): `ROOTS.public.proposalReview` (`roots.ts:107-109`), `email.service.ts:64`, `use-proposal-action-configs.ts:21-44`, `meeting-proposal-row.tsx:20`, `proposal-row.tsx:20`, `table/index.tsx:51`, `overview-card.tsx:88`, `edit-proposal-view.tsx:147,176`. No token use found in Zoho return URLs, GCal, funnels, tests, seeds or non-tmp scripts. `domains/permissions/lib/validate-share-token.ts` is dead code (zero callers).

### 4.3 Structure options (architect agent; recommendation, not a decision)

| | (a) `meetings.token` column | (b) `share_links` table | (c) both tokens side by side |
|---|---|---|---|
| Emailed-link permanence | breaks unless proposals keep a token too | clean — each legacy proposal token becomes a row | clean, but a dual path (against the non-defensive-migration rule) |
| Meetingless proposals (T5) | unreachable | row with `meetingId = null`, direct proposal scope | works, doubles the model |
| Backfill "which token wins per meeting?" | must pick | no question — every token carried forward | n/a |
| Revoke / rotate later | no | yes (row per link) | no |

- **Recommended: (b)** `share_links (id, token unique, meetingId nullable FK, focusProposalId nullable FK, createdAt, revokedAt)`. Same middleware cost as (a); legacy tokens are data, not a shim.
- **Migration order:** 1 create table + indexes → 2 backfill one row per existing proposal token (`meeting_id`, `focus_proposal_id = id`) → 3 ship the resolver and repoint every token-path procedure and route → 4 `create.before` stops writing `proposals.token`; a link is minted per meeting → 5 drop `proposals.token` + `shareable.tokenColumn` in a later, separately approved prod push. Steps 1–4 are additive (rollback = old path still live).
- **Pre-decision prod checks (read-only; owner runs):** `SELECT count(*) FROM proposals WHERE meeting_id IS NULL;` · `SELECT meeting_id, count(*) FROM proposals WHERE meeting_id IS NOT NULL GROUP BY 1 HAVING count(*) > 1 ORDER BY 2 DESC;` · `SELECT count(*) FROM proposals WHERE token IS NULL;` · `SELECT status, count(*) FROM proposals GROUP BY 1;`
- **URL:** `ROOTS.public.meetingReview(meetingId, token)` → `/proposal-flow/meeting/[meetingId]?token=…&proposal=<id>` (nuqs; default = the link's `focusProposalId`). The old `/proposal-flow/proposal/[proposalId]?token=` route redirects, resolved through the legacy token's `share_links` row.
- **Not building:** per-recipient links, revoke/rotate UI, a generic parent bridge for every shareable entity, a cross-meeting customer portal.
- **Spec split:** a new spec F, not blocked by A–E; shares the "selected proposal" naming with spec C.

### 4.6 nuqs pattern for `?proposal=` (context7 research agent, 2026-09-22; ✔ = spot-checked by me)

Installed nuqs **2.8.8** (latest 2.10.1). Everything below exists in 2.8.8; no upgrade needed (2.9.0 would fix an effect-update transient-state bug, #1368 — moot because we never write from an effect).

- **NQ1 Parser = shape only.** `createParser` that accepts a UUID and returns `null` otherwise (docs: parsers "always return null for invalid inputs"; parsers never validate against data). **No `withDefault`** — the default is data-derived. Membership in the meeting's proposals + the fallback rule (C30) is a pure resolver, `lib/resolve-selected-proposal.ts`, mirroring `resolveStageTradeId`.
- **NQ2 Absent/invalid → derive, never write back.** nuqs' model: the default "is internal to React, it will not be written to the URL". Only explicit user actions (select, create, duplicate) write `?proposal=`. Never seed from an effect (the class of bug the issue-29 attempt hit).
- **NQ3 Options:** `history: 'replace'` (docs: push "should be used sparingly to avoid breaking the Back button"; Back then leaves the meeting, consistent with `step`/`trade` today) · `shallow: true` (default; the view is React Query — `shallow: false` would re-run the RSC page per switch) · `scroll` default · `clearOnDefault` moot.
- **NQ4 Atomic update:** `useQueryStates({ proposal, trade })` and `setSelection({ proposal: id, trade: null })` — one URL write, `null` clears `trade`. This makes "switching proposals resets the stage trade" a single owner (today `step` and `trade` setters live in different components: `meeting-flow.tsx:63`, `trade-selection-provider.tsx:162,169`).
- **NQ5 One shared module,** imported from **`'nuqs/server'`** (server-safe, no `'use client'`): parser map + `createLoader` + `createSerializer` + `inferParserType`; hooks, page loader and link builder all read the same map (prefetch-key drift otherwise). Repo precedent: `campaigns-admin/constants/query-parsers.ts`. ✔ Today `meeting-flow/constants/query-parsers.ts:1` imports from `'nuqs'` — unusable from `page.tsx`.
- **NQ6 Server:** `createLoader` (not `createSearchParamsCache`, which is for deeply nested RSCs); `await loadMeetingFlowSearchParams(searchParams)` in the Next 15 page, then fire-and-forget `prefetch` + `<HydrateClient>` per `frontend-stack.md#server-prefetch-two-tiers`. ✔ `dashboard/meetings/[meetingId]/page.tsx` has no searchParams, loader, prefetch or HydrateClient today. No hydration mismatch: the app adapter sources state from the same URL the server parsed. Suspense: ✔ already provided by `dashboard/layout.tsx:33`; nothing extra.
- **NQ7 Links:** `createSerializer(map)` with a base path → `ROOTS.dashboard.meetings.flow(id, { proposal, step })`, replacing hand-built `URLSearchParams` (`roots.ts:89` `scheduleWithMeetingHighlight`). Layering question: `roots.ts` (shared/config) importing a feature parser map → the map probably belongs in `src/shared/lib/` once spec F's page reuses `?proposal=`. ✔ `src/shared/lib/url-parsers.ts` (`proposalIdParser = parseAsString.withDefault('')`) has **zero importers** — delete or replace.
- **NQ8 Testing:** `withNuqsTestingAdapter({ searchParams, onUrlUpdate })` + `renderHook`; assert `trade` cleared and `history === 'replace'`. **Blocker: the repo has no unit-test runner** (no vitest/jest, zero `*.test.*`) — smoke scripts or Playwright until one exists (V2).
- **NQ9 `?step` should become a slug** (`parseAsStringLiteral(STEP_IDS).withDefault(STEP_IDS[0])`, e.g. `?step=solution`): with steps renamed/removed (F8/F14), integer deep links silently shift meaning; invalid → default removes the "Invalid step" branch at `meeting-flow.tsx:270`. ✔ No stored or sent link carries `?step=N` today (push `--navigate`, GCal, emails: none) — **no redirect shim needed**. The zero-proposal gate (F1/S1) is resolver logic, not the parser.
- **Pitfalls:** `withDefault` on `proposal`; writing the resolved default from an effect; mixing `useSearchParams`/`router.push` with nuqs for the same keys (foreign writes bypass its queue); two copies of the parser map; rapid double-select inside the ~50 ms throttle (last write wins); on remote delete of the selected proposal let the resolver fall back — do not auto-rewrite the URL.
- **Recorded as requirements:** F3 (provider uses NQ1–NQ4), F14 (`?step` slug, NQ9), plus **F17** below.
