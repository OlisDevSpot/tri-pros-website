## 3. Placement — the modules question (owner's ask: SOW primitives colocated with construction?)

**Recommendation: tables + DAL + service in `modules/proposals/sow/`; the stored-reference primitives in `modules/construction/core/`.** Nothing table-shaped enters construction before P5 (C1/D1 intact).

Why the split falls this way:

1. **The rows are a proposals-aggregate child by every Sub-Entity Standard test** (ADR-0005 `:125-137`): same actor and trigger as the proposal, gated by the proposal lock ladder (`core/lib/proposal-lock.ts:59-70`), SUMmed into `proposals.final_tcp_cents`, cloned on duplicate, parent CASL subject reused. A `modules/construction/sow/` unit owning them would need `parent: { spec: proposalServerSpec }` and would import `recomputeProposalFinancials` — a construction → proposals edge that inverts the dependency direction. The catalog module's own DOCS already draws the line: its SOW is a **template**; the proposal's SOW is the proposal's (`construction/DOCS.md#neutral-schemas`; `ubiquitous-language.md:86`). Spec A has already named the unit (`modules/proposals/sow/`, §4.6) and promised "after W4, no caller changes".
2. **The `{ id, label }` reference shape is the duplication W4 is about to make worse.** It is defined **seven** independent times today — `proposals/core/schemas/index.ts:8-11` (`constructionItemSchema`), `entities/meetings/schemas/index.ts:28`, `meeting-flow/types/index.ts:258`, `meeting-flow/lib/trade-selection.ts:5-8`, `snap-sow-from-meeting.ts:10-16`, `google-calendar/lib/map-to-gcal.ts:9-10`, `x_application_trades` — plus four ad-hoc `{ id, label: name }` builders. W4's row↔domain mapper and scope rows would be the eighth and ninth. The construction design already assigns this primitive to the module (design §4 `:115-118`, §7.1, A9) and dropped it from P1 on a "zero call sites" claim that was true of *importers*, not of the shape.

## 4. W4 as it now stands (design inputs, not the spec)

### 4.1 DDL (all `text({ enum })`, no pgEnums — Addendum C)

> **Ruled shape (shape grill §6a, 2026-09-22).** A SOW item is a *priced work item* belonging to one trade and covering 1..N catalog scopes (G1). Catalog ids are `uuid` (G2); `*_label` and `kind` are Notion-era snapshots that retire at P5 (G2/G4).

- `proposal_sow_items`: `id uuid PK` (= Spec A's section id, lifted verbatim) · `proposal_id uuid FK cascade NOT NULL` · `position integer NOT NULL` · `title text NOT NULL` · `trade_id uuid NULL` · `trade_label text NULL` · `content_json jsonb NULL` · `content_html text NULL` · `section_price_cents bigint NULL` + `CHECK (IS NULL OR >= 0)` · `pain_points text[] NOT NULL DEFAULT '{}'` · `notes text NULL` · `created_at`/`updated_at`. Indexes `(proposal_id, position)`, `(trade_id)`. No `UNIQUE(proposal_id, trade_id)` (G1).
- `proposal_sow_scopes` (Q2, G3, G4): `id uuid PK` · `sow_item_id uuid FK cascade NOT NULL` · `position integer NOT NULL` · `scope_id uuid NOT NULL` · `scope_label text NULL` · `kind text({ enum: scopeKinds }) NULL` · timestamps. `UNIQUE(sow_item_id, scope_id)`; indexes `(sow_item_id, position)`, `(scope_id)`.
- `proposal_sow_cost_lines` (G3, G6): `id uuid PK` · `sow_item_id uuid FK cascade NOT NULL` · `position integer NOT NULL` · `label text NOT NULL` · `amount_cents bigint NOT NULL` + `CHECK (> 0)` · `related_scope_id uuid NOT NULL` · `notes text NULL` · timestamps. **Composite FK** `(sow_item_id, related_scope_id) → proposal_sow_scopes(sow_item_id, scope_id) ON DELETE CASCADE`. ### 4.2 Write side — the owner-approved brief (2026-09-22, supersedes the bullets it replaced; R9 ruled here)

**Principles in force (each verified in code/docs the same day).** P1 rows with identity are entities (own spec with `parent`, own `createCrudDal`, own hooks — Addendum B; built precedent `incentives/`). P2 every row write goes through its entity's five slots so hooks fire for every origin (`service-architecture.md#row-lifecycle-vs-orchestration`, `src/trpc/DOCS.md#crud-five-slots-fixed`; the incentives delete-all-and-insert is the one documented exception, not a pattern). P3 hooks carry the row's own invariants only; cross-entity composition and parent probes are service verbs; a DAL never imports a service (R.2). P4 a service is the crud spread + verbs + child services and is the one server API; routers are adapters (`service.ts` header, C17). P5 derived values re-drive from the hook of every row that is a term, through one idempotent chokepoint. P6 invariants on the entity, policies at the callsite. P7 scope comes from the spec, parent bridge included. P8 standing rulings: R.1 no tx in the save, R.4 nothing permissions-related, R.5 names get sign-off, non-defensive migration.

**Requirements (owner: "Looks good, lets proceed").**

1. **Four row kinds, four cruds.** Items, scope rows and cost-line rows each get a spec with `parent: { spec, fk }` and their own crud. Section incentives reuse `proposalIncentiveCrud` (same table, G7). *P1.*
2. **No hand-written SOW writes.** The unit has no `mutations.ts`; every insert/update/delete of a SOW row is a slot call. *P2.*
3. **Hooks hold only the row's invariants.** Item rows: lock gate (R7a) + pre-draft promotion (Spec A §4.4). Scope and cost-line rows: lock gate. Incentive rows: their existing recompute + the gate their `crud.ts` header defers to W4. One gate helper; each factory resolves its proposal id its own way. *P3, P5.*
4. **Services compose slots.** `proposalService.sow` = the item service, with `scopes` and `costLines` child services in the root's getter shape; section incentives stay on `proposalService.incentives`. No verb writes a row except through a slot. *P4.*
5. **Batch = reconcile-by-key, written once.** Incoming keyed list vs current rows: absent → delete, present → update, new → create, `position` = array order. One helper serves `replace`, duplicate's clone, and later the global incentives `replace` (retiring the P2 exception). Keys: item / cost line / section incentive by their form-minted uuid; scope row by catalog scope id (the G3 unique). *P2, DRY.*
6. **The helper is importable by a DAL hook.** Spec A puts SOW cloning in the proposal's `duplicate.after`; a hook may not import a service, so the reconcile helper lives at the DAL-lib level over crud handlers (the `upsertOneToOne` sibling). *P3.*
7. **Writes are partial.** A row update carries only the columns that changed; an untouched row arrives as `{}` and hits the engine's no-op; a child list is reconciled by key so adding one scope touches one row. The editor sends what the rep changed, keyed by section id, and never overwrites a field it did not touch. **This is the R9 answer**; the residual conflict is the same field on the same row from two devices (C41 realtime is the UX for that).
8. **One namespace, no adapters.** `proposals.sow` composes `createCrudRouter` from the item spec, the two child specs, and one `replace` procedure; scope resolution is the specs' own. *P4, P7.*
9. **Specialties writes single rows.** A scope toggle is one `scopes.create`/`scopes.delete`; content edits are an item `update`. Content-only becomes its callsite policy (revises Spec A C56's verb restriction). SA17's cascade is the composite FK. *P6.*
10. **One read, one hydrator.** The aggregate read returns items with children; `toSowInputs` maps rows → `SOW[]` for the form, the PDF and readiness. Cents at the DAL, dollars in the domain (the funding pair's pattern).
11. **Failure model.** Sequential slot calls, no tx (R.1). Reconcile is idempotent by construction (a retry of the same payload converges); a failed row surfaces as the DAL error.
12. **Recompute cost accepted.** Incentive rows re-drive per row; a save touching three section incentives recomputes three times. No dedupe at today's sizes.
13. **Names are the precedent applied.** `proposalSowItem…`, `proposalSowScope…`, `proposalSowCostLine…` for spec/crud/service; verbs reuse `replace`; locked names stand; the reconcile helper is the only new word (R.5).

**Non-goals:** no transaction, no permissions work, no sixth slot, no optimistic version check, no nested children on item slots, **no whole-SOW write of any kind (ruled 2026-09-23, below)**.

**RULED 2026-09-23 (owner): GRANULAR — one user action, one slot call.** The owner rejected the reconcile-by-key batch ("way too many new primitives … rather than building this properly from the core") and asked for research on whole-replace vs adding/removing one row at a time.
