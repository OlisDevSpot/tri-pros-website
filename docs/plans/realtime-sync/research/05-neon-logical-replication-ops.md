## 1. Enabling logical replication on Neon

- **Scope: project-level, not branch-level.** "Enabling logical replication changes the PostgreSQL `wal_level` setting from `replica` to `logical` for all databases in your Neon project." (logical-replication-neon). OpenAPI field `settings.enable_logical_replication`: "Sets wal_level=logical for all compute endpoints in this project. All active endpoints will be suspended. Once enabled, logical replication cannot be disabled." → applies to `production`, `development`, and every `wt/*` branch.
- **Irreversible.** "Once changed, it cannot be reverted." (logical-replication-neon; same sentence on concepts, guide index, and the Neon→Postgres guide). The only way back is a new project.
- **Restarts computes / drops connections.** "Enabling logical replication also restarts all computes, so active connections will be dropped and have to reconnect." (docs) / "All active endpoints will be suspended." (API). Our `pg` Pool must tolerate a one-time drop.
- **Steps.** Console: Project → **Settings → Logical replication → Enable**. CLI: `neon projects update polished-shape-00174668 --enable-logical-replication --yes`. API: `PATCH /api/v2/projects/polished-shape-00174668` body `{"project":{"settings":{"enable_logical_replication":true}}}`. Verify: `SHOW wal_level;` → `logical`. (logical-replication-neon.)
- **Plan restriction: none.** "Neon's logical replication feature, available to all Neon users" (logical-replication-guide). Free plan is fine for the switch itself; the *consequences* (§3) are plan-bound.
- **Separate-projects case (hypothetical):** you'd enable per project; a dev-only project could stay `replica`.

## 2. Replication slots on Neon

- **Inactive-slot removal — exact wording:** "To prevent storage bloat, Neon automatically removes _inactive_ replication slots after approximately 40 hours. … An inactive replication slot is one that doesn't acknowledge `flush_lsn` progress for more than approximately 40 hours. This is the same `flush_lsn` value found in the `pg_stat_replication` view." Causes listed: "a dead subscriber" or "a long replication delay configured on the subscriber". Mitigation: keep the subscriber reporting `flush_lsn` more often than every 40 h; "If increasing replication frequency is not possible, please contact Neon Support for alternatives." Recreate per the subscriber's instructions if removed. (logical-replication-neon#unused-replication-slots.) **UNVERIFIED edge:** whether a *connected but write-idle* consumer (no WAL to ack, so `flush_lsn` cannot "progress") counts as inactive after 40 h. Neon's wording is about acknowledging progress; test on the dev branch before relying on it.
- **Max slots / senders:** `max_replication_slots = 10`, `max_wal_senders = 10`; "If you require different values … contact Neon support." (logical-replication-neon#publisher-settings; live SQL confirms 10/10.) Two of the 10 slots are already used by Neon-internal physical slots (`wal_proposer_slot`, `wal_retention_slot`) — so effectively ≤8 logical slots per branch.
- **Branch restore:** "Restoring a branch will delete all replication slots on that branch. Replication slots are not automatically re-created during the restore process." (logical-replication-neon#important-notices.) Instant restore is root-branch-only (`production`), and the API's restore endpoint is also what **Reset from parent** uses ("use the Restore branch endpoint, specifying the parent branch ID as the `source_branch_id`" — reset-from-parent). **UNVERIFIED:** Neon does not state explicitly that reset-from-parent drops slots on the child; assume it does (same mechanism, and the child's timeline is replaced). Electric treats a "Postgres timeline change" as a full-purge event (§8).
- **Branch create:** Neon documents only the subscriber side: "subscriptions defined on a parent branch are not duplicated on child branches; they are dropped … before the compute associated with the child branch starts" (creating, resetting, restoring). **UNVERIFIED (undocumented):** whether publisher-side slots/publications are copied to a new child. Publications are catalog rows (`pg_publication`) and will copy with the data; slot state is not part of the data timeline in Postgres, so expect **no slot on a fresh child**. Plan on one Electric instance + slot per branch you want synced (§7).
- **Compute restart / suspend:** Postgres: "Slots persist independently of the connection using them and are crash-safe … The current position of each slot is persisted only at checkpoint, so in the case of a crash the slot might return to an earlier LSN, which will then cause recent changes to be sent again" (PG17 logicaldecoding-explanation). Neon's 40-hour policy only makes sense if slots outlive the compute; Neon does not document the mechanism. **UNVERIFIED:** slot survival across Neon scale-to-zero specifically; the Electric config docs say `ELECTRIC_REPLICATION_IDLE_TIMEOUT` "enables database scale-to-zero on supported providers" and warns "inactive replication slots cause Postgres to retain WAL files" — i.e., Electric expects the slot to persist while the DB is suspended.
- **WAL retention when Electric is down.** PG17: a slot's `restart_lsn` is "the oldest WAL which still might be required by the consumer of this slot and thus won't be automatically removed during checkpoints unless this LSN gets behind more than `max_slot_wal_keep_size`"; with `-1` (PG default) "replication slots may retain an unlimited amount of WAL files"; `wal_status` goes `reserved → extended → unreserved → lost`, `invalidation_reason = wal_removed`. **Neon bound:** (a) the 40-hour inactive-slot removal above; (b) **conflicting evidence on `max_slot_wal_keep_size`** — Neon changelog 2024-01-12: "For logical replication, the PostgreSQL `max_slot_wal_keep_size` is now set to 1 GB, limiting the maximum size of WAL files that replication slots are allowed to retain"; but the current compatibility page's parameter table does not list it, and our live value is `-1` (with `wal_level=replica`). **UNVERIFIED which applies once enabled — run `SHOW max_slot_wal_keep_size` immediately after flipping the switch.** If 1 GB applies, an Electric outage that accumulates >1 GB of WAL on published tables invalidates the slot (`lost`) → full resync (§8). Neon does not let you set it yourself ("Postgres parameters are not user-configurable outside of a session, database, or role context"; Scale plan may ask Support).
- **Storage billing impact:** Neon states the 40-hour rule exists "to prevent storage bloat" and that the history window "directly affects **History** on your usage dashboard". **UNVERIFIED** which meter slot-retained WAL lands on (Storage vs History) and whether the Free plan's "6 hours, up to 1 GB-month" history cap interacts with slot retention. Free plan: exceeding the 0.5 GB storage cap "causes operations that increase storage (inserts, updates, and deletes) to fail until you free space or upgrade" (plans FAQ).

## 3. Autosuspend interaction

- **Yes — an active replication connection keeps the compute awake.** "While a logical replication subscriber is connected, your Neon compute stays active and will not scale to zero. Neon does not 'disable' scale to zero; the database is simply always active because replication keeps it in use … This results in ongoing compute usage and can significantly affect your bill." Neon's check: `SELECT * FROM pg_stat_replication WHERE application_name != 'walproposer';` — "If the count is greater than 0, a Neon compute where the publishing Postgres instance runs will not be suspended." (logical-replication-neon#logical-replication-and-scale-to-zero; repeated on scale-to-zero, scale-to-zero-guide, and logical-replication-postgres.) Electric holds exactly such a walsender while running.
- **`suspend_timeout_seconds: 0`** (all our endpoints): OpenAPI — "`0` uses the plan default; `-1` disables scale-to-zero (never suspends). Minimum is plan-dependent (Scale: 60); maximum 604800 … Free cannot change it; Launch can only enable or disable; Scale can set any value." Plan default = 300 s (scale-to-zero-guide). So today: 5-min autosuspend on every branch.
- **Escape hatch (Electric-side):** `ELECTRIC_REPLICATION_IDLE_TIMEOUT` — "After seeing no activity on the logical replication stream for this long, Electric will close all of its database connections." Default `0` (disabled); "Incoming requests reopen connections automatically"; warning: "Avoid setting this with constant database writes, as inactive replication slots cause WAL accumulation." (electric.ax config.) Trade-off: compute can sleep, but the slot goes inactive (40-h clock starts) and the next shape request pays a cold-start.
- **Cost of 24/7 at the 0.25 CU floor** (Neon bills a fixed 744-h month; CU-hours = size × hours; Launch $0.106/CU-h, Scale $0.222/CU-h, Free 100 CU-h/project/month included — plans + usage-calculations):
  - 0.25 CU × 744 h = **186 CU-h/month** minimum (more whenever autoscaling lifts it above 0.25).
  - **Launch:** 186 × $0.106 ≈ **$19.72/month** per always-on branch. **Scale:** 186 × $0.222 ≈ **$41.29/month**.
  - **Free (our plan today):** 186 CU-h > 100 CU-h allowance → exhausted after 400 h ≈ **16.7 days**, then "your compute is suspended until the next billing period or until you upgrade" (plans FAQ). Electric on prod is **not viable on Free**.
  - **Today's baseline:** 11.0 CU-h in 160.9 h → ≈ 51 CU-h/month at the current rate (avg 0.256 CU while awake, 27% duty cycle). Incremental cost of always-on ≈ +135 CU-h/month (Launch ≈ +$14.3, Scale ≈ +$30). Double it if Electric also holds the `development` branch awake (that compute is capped at 1 CU max, same 0.25 floor).
  - Not in the compute line: **public network transfer** — "Public network transfer includes data sent via logical replication to any destination" (plans). Free 5 GB/project/month, paid 500 GB then $0.10/GB. Current usage 0.23 GB/7 d. REPLICA IDENTITY FULL (§6) inflates the stream.
- **Always-on maintenance obligation:** "If you disable scale to zero entirely … you will have to manually restart your compute to pick up the latest updates … a weekly compute restart is recommended" (scale-to-zero-guide). Updates otherwise apply to "Computes that have been active for 30 days or more" or on restart (updates).

## 4. Connection details

- **Direct, not pooled — both vendors.** Neon: "When a subscriber connects to a Neon publisher, use a direct connection string, not a pooled one. Logical replication requires a persistent connection and is not compatible with connection poolers. Make sure the connection string … does not include the `-pooler` suffix" (logical-replication-neon#subscriber-access; pooling table row "Logical replication | Direct | Requires persistent connection"). Electric: "You usually want to connect directly to Postgres and not via a connection pool" (deployment); Neon page: "don't check 'Pooled connection'. You want the direct connection string in order to use logical replication."
  - Our direct hosts: prod `ep-flat-wind-afvc0zla.c-2.us-west-2.aws.neon.tech`, dev `ep-mute-sunset-afxp3pn5.c-2.us-west-2.aws.neon.tech` (drop `-pooler`). The Console's pooling toggle "just switches the displayed connection string"; both hosts are always live.
  - Electric can take `ELECTRIC_POOLED_DATABASE_URL` for non-replication queries — "may point to a connection pooler, but must target the same database instance" and that user "doesn't need `REPLICATION` role". Use the `-pooler` host there if desired. Direct-connection budget: `max_connections` for 0.25–2 CU autoscaling = 839 (compatibility formula); Electric's `ELECTRIC_DB_POOL_SIZE` default 20.
- **sslmode.** Electric config: "For encrypted connections, set `sslmode=require`"; "Electric doesn't support `sslmode=verify-ca` or `sslmode=verify-full`"; `ELECTRIC_DATABASE_CA_CERTIFICATE_FILE` enables server-identity verification if you want it. **UNVERIFIED:** whether Electric accepts/ignores Neon's `channel_binding=require` URL parameter; strip it if Electric errors on parse.
- **Role privileges.** PG17: replication connection role "must have the `REPLICATION` attribute (or be a superuser)", `LOGIN`, and `SELECT` on published tables; "To create a publication, the user must have the `CREATE` privilege in the database"; "To add tables to a publication, the user must have ownership rights on the table"; `FOR ALL TABLES` / `FOR TABLES IN SCHEMA` require superuser. Electric (postgres-permissions): automatic mode needs `REPLICATION`, `SELECT`, `CREATE` on database, and **table ownership** "to set REPLICA IDENTITY FULL and add tables to publications"; manual mode (`ELECTRIC_MANUAL_TABLE_PUBLISHING=true`) needs only `REPLICATION` + `SELECT` with the DBA pre-creating publication, tables, replica identity, and publication ownership.
- **Does `neondb_owner` suffice? Yes.** Verified live: `rolreplication=true`, `CREATE` on `neondb`, owns all 50 tables. Neon: default role and Console/CLI/API-created roles are `neon_superuser` members (which carries `REPLICATION`); "Roles created via SQL do not have this privilege, and the `REPLICATION` privilege cannot be granted." No superuser on Neon → Electric's explicit-table publication is the only option (fine; that is Electric's default). If you create a dedicated `electric` role via Console/API as Neon recommends, it will *not* own the tables → either grant ownership or use manual publishing.
- **IP allow-list.** Neon IP Allow is **Scale-plan only**; our `allowed_ips` is empty, so nothing to do. If ever enabled: "Determine the IP address … of the subscriber … add the IPs to your IP Allow list." Electric Cloud static egress IPs: **UNVERIFIED — not documented** on electric.ax (cloud, cloud/usage, security pages only say the DB "must be reachable from Electric Cloud"). Self-hosted Electric's egress IP is whatever your host gives you.
- **Electric Cloud** (for reference): "connects to your Postgres, consumes changes over logical replication"; PAYG "$1 per 1M writes", "$0.10 per GB·month" retention, invoices under $5 waived; Pro $249/mo; Scale $1,999/mo (pricing page).

## 6. Schema-change workflow

- **Postgres semantics (PG17):** "The database schema and DDL commands are not replicated"; "DDL operations are not published" (CREATE PUBLICATION). `FOR ALL TABLES` "replicates changes for all tables in the database, including tables created in the future" but requires superuser and "It is not possible to add or drop tables from a publication defined with `FOR ALL TABLES`" (Neon tips). Explicit `FOR TABLE` lists: "Objects must be added explicitly." `ALTER PUBLICATION … ADD TABLE` requires owning the publication and the table. When a table in a publication is dropped: **not stated in PG docs**; `pg_publication_rel` is a catalog mapping, so the row goes with the table (inference). Electric side is what matters (below).
- **REPLICA IDENTITY:** "A published table must have a replica identity configured in order to be able to replicate `UPDATE` and `DELETE` operations"; DEFAULT = "Records the old values of the columns of the primary key"; FULL = "Records the old values of all columns in the row" (ALTER TABLE). Electric **requires and sets FULL itself** ("Sets `REPLICA IDENTITY FULL` on tables (requires table ownership)") when it adds a table to `electric_publication_default`. Consequence for us: every UPDATE/DELETE on a shaped table logs the full old row — including JSONB columns — into WAL, the replication stream, and Neon egress. All 50 tables are `d` today; Electric will flip shaped ones to `f`.
- **Electric's publication:** created automatically as `electric_publication_default` (suffix from `ELECTRIC_REPLICATION_STREAM_ID`), tables added "as shapes are requested" — an explicit list, never `FOR ALL TABLES`. New tables from `drizzle-kit push` are therefore *not* published until a shape asks for them.
- **What happens to shapes (Electric shapes guide):** "When the schema of a table used by a shape changes — for example, adding, removing, or renaming a column — Electric automatically invalidates all shapes on that table." Detection: (1) pgoutput Relation messages ("a new Relation message will be sent if the relation's definition has changed" — PG17 protocol), (2) "a background process checks every 60 seconds whether cached table metadata still matches the actual database schema". Clients get "a `409 Conflict` response or a `must-refetch` control message", "discard local shape data … re-sync from scratch"; the TypeScript client / TanStack DB do this automatically. **No Electric restart required.** Dropping a table: "you need to _manually_ delete all shapes that are defined on that table" (`DELETE /v1/shape`), especially before recreating it. Enum changes (`ALTER TYPE … ADD VALUE`): no Relation message (the relation's definition is unchanged; pgoutput sends a Type message with the type *name* for non-built-in OIDs) → **UNVERIFIED** whether Electric invalidates; expect new labels to flow through as text. Shape `where` clauses: enums "must be explicitly cast to text"; JSONB operators unsupported; uuid/text/numeric/bool/date/arrays supported.
- **`drizzle-kit push`:** "Reads your schema … Introspects database … Generates migrations … Applies changes" directly, "omitting SQL files generation"; `--force` "auto-accept[s] all data-loss statements". It emits CREATE/ALTER/DROP TABLE and CREATE TYPE/enum DDL. None of that breaks a Postgres publication (DDL isn't published; a dropped table just leaves the publication). What it *does* do: every column add/drop/rename on a shaped table → Electric invalidates that table's shapes → all connected clients refetch. **UNVERIFIED:** whether drizzle-kit's introspection diff ever resets `REPLICA IDENTITY` (it is not a drizzle-managed property; Electric's 60-s reconciler would re-detect anyway) and whether push emits a transaction wrapper. Operational rule that follows from the docs: run `pnpm db:push:prod` when a burst of full resyncs is acceptable; add new tables before requesting shapes on them; never rely on `FOR ALL TABLES`.

## 7. Branching / dev workflow

- Enabling is project-wide (§1), so `development` and every `wt/*` branch get `wal_level=logical` too. That alone costs nothing; what costs is a connected consumer.
- "Each branch in a Neon project has its own Postgres instance" (logical-replication-neon). Slots and publications are per-instance, so **each branch you want Electric on needs its own Electric instance (or `ELECTRIC_REPLICATION_STREAM_ID`) pointing at that branch's direct host**, which then holds *that* branch's compute awake (§3). On Free, a dev Electric left running burns the shared 100 CU-h/project pool at the same 0.25 CU/h as prod.
- Slots on new/reset branches: not copied (§2, partly UNVERIFIED) — a new `wt/*` branch starts with no Electric slot; Electric creates one on first connect. Reset-from-parent / restore replaces the timeline → Electric purges all shapes ("Postgres timeline change") and clients resync; Neon says restore deletes slots and does not recreate them.
- Branch archiving (Free): branches "Older than 14 days" and "not accessed for the past 24 hours" are archived, but a branch "cannot be archived if it … Has computes running" — an attached Electric prevents archiving of a dev branch; stopping Electric for a weekend lets the slot go inactive (40 h) → removed → full resync on Monday (cheap on 16 MB).
- **Local dev per Electric docs:** the installation guide's Docker Compose runs `postgres:16-alpine` with `wal_level=logical`, `listen_addresses=*`, port `54321:5432`, and `electricsql/electric:latest` with `DATABASE_URL=postgresql://postgres:password@postgres:5432/electric?sslmode=disable`, `ELECTRIC_INSECURE: true` ("Not suitable for production"). Alternatively "connect Electric to an existing Postgres database by running the container independently with the appropriate `DATABASE_URL`". Trade-off for us: local Postgres = no Neon cost, no 40-h slot clock, no wake-ups, but a schema/data copy to maintain (`drizzle-kit push` against it; we have no migration files); Neon dev branch = real data, but always-on dev compute while Electric runs and the slot-removal dance when it doesn't. `ELECTRIC_REPLICATION_IDLE_TIMEOUT` is the documented middle path for dev.
- Separate-projects case (hypothetical): a dev project could stay unflipped and use local Docker Postgres for Electric; prod project flips. Not our layout.

## 8. Failure modes & recovery

- **Slot removed by Neon (40 h inactive) or otherwise lost.** Electric: "the new slot starts from the current WAL position with no history. This means all existing shapes are invalidated. Clients will receive `409` (must-refetch) responses and must perform a full resync of their shapes." "When Electric restarts, it will recreate the slot and rebuild shape logs from scratch." No manual step beyond (optionally) dropping a stale slot; expect "a temporary load spike" on Neon and on Electric.
- **Electric down for hours.** "When Electric isn't running, its replication slot remains but becomes inactive. WAL accumulates indefinitely until Electric reconnects or the slot is removed." Compute: with no walsender, Neon *can* scale to zero (the `pg_stat_replication` check returns 0), so no compute cost while Electric is down — but WAL is retained by the slot. Bound: Neon's 40-h removal, and possibly the 1 GB `max_slot_wal_keep_size` (§2, UNVERIFIED) → `lost` slot → "Electric will detect this, drop all shapes, and recreate the slot." Electric's own advice: "If stopping Electric for an extended period, remove the replication slot" (`SELECT pg_drop_replication_slot('electric_slot_default');`). Neon's `ALTER SYSTEM SET max_slot_wal_keep_size` recommendation from Electric is **not possible on Neon** (no superuser/instance params).
- **Maintenance-window restart (Sunday 09:00–10:00 UTC on Free, Neon-scheduled; "typically takes only a few seconds"; "Brief connection drops are expected").** Slot survives (crash-safe; may rewind to last checkpoint and resend recent changes — PG17). Electric reconnects on its own; docs don't specify its backoff, but "Electric persists shape data to disk … shapes will survive server restarts without needing to re-sync" as long as the *same* slot is reused and storage is persistent. Also "Neon occasionally performs essential platform maintenance outside of scheduled updates … may require compute restarts". Neon's `wal_sender_timeout` is 10 s (live) vs PG default 60 s; Neon tips say timeouts can be raised only "with assistance from Neon Support".
- **Free-plan CU-hour exhaustion.** Compute suspended until the next period → Electric loses its connection; if the outage exceeds ~40 h the slot is removed → full resync when service resumes.
- **Restore / reset / PITR.** Neon deletes slots on restore and does not recreate; Electric purges all shapes on timeline change → clients resync; Electric must be restarted or will recreate the slot on reconnect.
- **Two Electric instances on one slot** (e.g., blue/green deploy): the second fails "replication slot … is active for PID …"; Electric's upgrade guide prescribes shared storage or temporary slots (`CLEANUP_REPLICATION_SLOTS_ON_SHUTDOWN=true` + random slot name — "Unclean shutdowns cause shape rotations"). Temporary slots also sidestep the 40-h rule at the cost of a resync on every Electric restart.
- **Monitoring hooks:** `neon inspect db replication-slots` (CLI), `pg_replication_slots.wal_status/inactive_since/invalidation_reason`, `pg_stat_replication.flush_lsn`; Neon Console Monitoring retention on Free is 1 day.

## 9. Bottom line — what changes if we flip `enable_logical_replication`

1. **Irreversible, project-wide:** `wal_level=logical` on `production`, `development`, and all `wt/*` branches forever; one-time restart of every active compute (drops app connections).
2. **Compute becomes always-on wherever Electric is connected** — Neon will not suspend a publisher with a walsender. Prod alone ≈ 186 CU-h/month at the 0.25 CU floor (vs ≈ 51 today): **exceeds the Free plan's 100 CU-h and suspends prod after ~17 days** → a paid plan is a precondition (Launch ≈ $19.72/mo per always-on branch, Scale ≈ $41.29/mo). Dev-branch Electric doubles it.
3. **New failure clock:** any consumer idle >~40 h loses its slot → Electric recreates it and every client does a full resync. Electric outages also accumulate slot-held WAL, possibly capped at 1 GB by Neon (verify post-enable).
4. **Schema changes become client-visible events:** each `drizzle-kit push` that touches a shaped table's columns invalidates those shapes (409/must-refetch); dropped tables need manual shape deletion. Electric flips shaped tables to `REPLICA IDENTITY FULL` (bigger WAL/egress; egress counts toward the 5 GB Free / 500 GB paid allowance).
5. **Connection-string change for Electric only:** direct host (no `-pooler`), `sslmode=require`, `neondb_owner` suffices (verified privileges/ownership); app keeps its pooled URLs.
6. **New infrastructure to run/monitor:** an Electric service (Docker, persistent NVMe-class `ELECTRIC_STORAGE_DIR`, `ELECTRIC_SECRET` behind an auth proxy) per synced branch, plus watching `pg_replication_slots` and the Neon compute-hours meter; weekly compute restarts if scale-to-zero is effectively disabled.
7. **Dev workflow:** either run Electric against local Docker Postgres (`wal_level=logical`, zero Neon cost) or accept an always-on dev compute + the 40-h slot dance; `ELECTRIC_REPLICATION_IDLE_TIMEOUT` mitigates but restarts the inactivity clock.
8. **Docs gap to remember:** neither vendor's Electric↔Neon guide mentions items 2–3; Neon's community guide pins Electric 1.0.17 (current 1.8.0).
