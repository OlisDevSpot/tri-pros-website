## 2. Shape model

**Definition** — a shape = `table` (+ optional `where`, `columns`, `queryable_columns`). "Shapes are currently single table, though you can use subqueries to filter based on related data." "While you can use subqueries to filter rows based on data in other tables, the shape only contains rows from the root table—not the related data itself." To sync related data: multiple shapes + client-side join, or denormalise. Partitioned tables supported (partition or root). Table may be schema-qualified (`foo.projects`; default `public`). ([Shapes guide](https://electric.ax/docs/sync/guides/shapes))

**WHERE subset** (verbatim table in the guide):
- Column types: "numerical types, `boolean`, `uuid`, `text`, `interval`, date and time types (with the exception of `timetz`), Arrays (but not yet Enums, except when explicitly casting them to `text`)".
- Operators: comparison `= <> < > <= >=`; logical `AND OR NOT`; arithmetic; bitwise (ints); string `|| LIKE ILIKE NOT LIKE NOT ILIKE`; array `= <> || @> <@ &&`; `IS [NOT] NULL`; boolean tests; `IS [NOT] DISTINCT FROM`; membership `IN`, `NOT IN` "Including subqueries: `value IN (SELECT ...)`"; `BETWEEN` variants; quantified `= ANY(array)`, `<> ALL(array)`.
- Functions: `lower() upper() like() ilike() coalesce() greatest() least() array_cat() array_prepend() array_append() array_ndims() timezone() justify_*()`.
- **Unsupported** (verbatim section "Unsupported operators"): "**JSONB operators**: `@>`, `<@`, `?`, `?|`, `?&`, `@?`, `@@`, `#>`, `#>>`, `-`, `#-`, `jsonb_path_exists()`, etc."; full-text search operators; geometric operators. Also "can't use non-deterministic SQL functions like `count()` or `now()`". Positional params `$1…` supported and recommended against injection.
- **Subqueries**: "Electric supports subqueries in where clauses … memberships, sharing rules, parent-child traversal, and exclusions." Example: `id IN (SELECT user_id FROM memberships WHERE org_id = $1)`; compound `owner_id = $1 OR id IN (SELECT document_id FROM document_shares WHERE shared_with = $1)`. ([Shapes guide](https://electric.ax/docs/sync/guides/shapes))
- **EXISTS is not supported.** Parser source: `defp node_to_ast(%PgQuery.SubLink{location: location}, _, _, _) do {:error, {location, "only \`value IN (SELECT ...)\` sublinks are supported right now"}}`; the matching clause accepts only `sub_link_type: :ANY_SUBLINK` with empty `oper_name` (i.e. `IN (SELECT …)`). Aggregation: "aggregation is not supported in this context". ([parser.ex L888–933](https://github.com/electric-sql/electric/blob/main/packages/sync-service/lib/electric/replication/eval/parser.ex))

**Move-in / move-out** — "When a shape uses a subquery, Electric tracks the dependency between tables. If the data in the subquery changes (e.g., a project becomes archived), rows will automatically move in or out of the shape without the row itself being modified. Electric keeps these moves incremental even for compound expressions that use `AND`, `OR`, and `NOT` around subqueries. In older releases those cases could return `409` and force a full resync of the shape." For plain (non-subquery) WHERE clauses, a row whose column change makes it enter/leave the predicate is delivered as insert/delete in the log (implied by the log model; explicit doc sentence not found → **UNVERIFIED wording**). ([Shapes guide](https://electric.ax/docs/sync/guides/shapes))

**Handles / offsets / 409** — First request `offset=-1` returns snapshot pages (`electric-offset` header, client paginates), then `live=true&handle=…&offset=…` long-polls. Control messages: `up-to-date`, `must-refetch`, `snapshot-end`. "When a shape handle is deleted, clients receive a `409 Conflict` response or a `must-refetch` control message. This tells the client to discard its local data and re-sync the shape from scratch." Handles are deleted on: **replication slot invalidated** (`max_slot_wal_keep_size` exceeded → "full shape purge"), **schema changes** ("adding, removing, or renaming a column — Electric automatically invalidates all shapes on that table"; detected via relation messages and a 60-second reconciliation), **`ELECTRIC_MAX_SHAPES` LRU eviction**, **explicit `DELETE /v1/shape`** (requires `secret`). `offset=now` skips history; `log=changes_only` skips the snapshot. ([Shapes guide](https://electric.ax/docs/sync/guides/shapes); [HTTP API](https://electric.ax/docs/sync/api/http))

**Immutability** — "Shape definitions are currently immutable. Once a shape subscription has been started, its definition cannot be changed." Changing a WHERE = new shape. ([Shapes guide](https://electric.ax/docs/sync/guides/shapes))

**Subset snapshots** — client can `requestSnapshot()` with `where/params/orderBy/limit/offset` (POST supported to avoid URL limits; `queryable_columns` allow-lists what clients may query). ([Shapes guide](https://electric.ax/docs/sync/guides/shapes); [HTTP API](https://electric.ax/docs/sync/api/http))

**Limits / throughput** — No documented max shape size; benchmark: "a single client syncing a single large shape of up-to 1M rows. The sync time is linear, the memory is stable." Response chunking `ELECTRIC_SHAPE_CHUNK_BYTES_THRESHOLD` default `10485760`. Shape count unlimited unless `ELECTRIC_MAX_SHAPES` set. Write throughput: "With optimized where clauses [`field = constant`, `field IN list`, `field IN (subquery)`, AND/OR combos] … ~5,000 row changes per second no matter how many shapes"; "With non-optimized where clauses, throughput is inversely proportional to the number of shapes. If you have 10 shapes, Electric can process 1,400 changes per second. If you have 100 shapes, throughput drops to 140 changes per second." ([Shapes guide](https://electric.ax/docs/sync/guides/shapes); [Benchmarks](https://electric.ax/docs/sync/reference/benchmarks); [Config](https://electric.ax/docs/sync/api/config))

**Compaction** — 1.0.0 CHANGELOG: "Add compaction flag allowing UPDATE events to be compacted for bandwidth savings"; code exists (`shape_cache/pure_file_storage`, `shapes/api/params.ex`) but **no user-facing config/HTTP doc found → how to enable is UNVERIFIED**. ([CHANGELOG](https://raw.githubusercontent.com/electric-sql/electric/main/packages/sync-service/CHANGELOG.md); GitHub code search)

## 4. Deployment options

**(a) Electric Cloud** — Was GA with self-serve pricing from 2026-04-02 (PAYG $0 + bills under $5 waived; Pro $249/mo; Scale $1,999/mo 6-mo commit; Enterprise custom; metered on writes $1/1M and retention $0.10/GB-month; "Postgres Sync add-on: $2 per million writes emitted to the shape log"; reads/egress/fan-out free; "Postgres subqueries" listed as a Pro feature). **As of 2026-08-11: "Electric Cloud is winding down. Cloud users will need to self-host or move to another provider."** No sunset date published; the `/cloud` page still shows "Start building now" with the Databricks banner. Regions: none published. Source connection model: dashboard-issued `source_id` + `secret` query params (seen in repo example). **Do not plan on Cloud.** ([Databricks post](https://electric.ax/blog/2026/08/11/electric-joining-databricks); [Pricing](https://electric.ax/pricing); [Pricing post](https://electric.ax/blog/2026/04/02/electric-cloud-pricing); [/cloud](https://electric.ax/cloud); [proxy-auth route.ts](https://github.com/electric-sql/electric/blob/main/examples/proxy-auth/app/shape-proxy/route.ts))

**(b) Self-host** — Docker `electricsql/electric:<ver>`. Required env: `DATABASE_URL`, `ELECTRIC_SECRET` (or `ELECTRIC_INSECURE=true`, dev only). Storage: "Electric caches Shape logs and metadata on the filesystem" → `ELECTRIC_STORAGE_DIR` (default `./persistent`); "Your Electric host must provide a persistent filesystem. Ideally this should be large, fast and locally mounted, such as a NVMe SSD." Ephemeral disk = full resync every restart. Shape metadata in SQLite (NFS/EFS corruption caveat; `ELECTRIC_SHAPE_DB_EXCLUSIVE_MODE`). Port `ELECTRIC_PORT` default `3000`. Cache headers `ELECTRIC_CACHE_MAX_AGE=60`, `ELECTRIC_CACHE_STALE_AGE=300`. Concurrency `ELECTRIC_MAX_CONCURRENT_REQUESTS` `{"initial":300,"existing":10000}`. Platforms documented: AWS, GCP, Digital Ocean, Fly.io, Render (Render example: 20 GB persistent disk). CPU/RAM sizing numbers: **not documented (UNVERIFIED)** — docs only rank "disk speed > memory > CPU". Rolling upgrades need shared storage + advisory lock (`/v1/health` returns 202 `waiting`) or separate stream IDs. ([Deployment](https://electric.ax/docs/sync/guides/deployment); [Config](https://electric.ax/docs/sync/api/config); [Upgrading](https://electric.ax/docs/sync/guides/upgrading); [Render](https://electric.ax/docs/sync/integrations/render))

**(c) On Vercel** — No. Vercel page: "you'll need a hosting platform that supports long-running processes"; you can deploy the *app* on Vercel and host Electric elsewhere. Additional Vercel caveat: "Vercel's CDN can cache responses when you proxy requests to an external Electric service … cache keys are not configurable and may not differentiate between requests with different query parameters" → add `CDN-Cache-Control: no-store` and `Vercel-CDN-Cache-Control: no-store` headers for the proxy route in `vercel.json`. Also note each `live=true` poll holds the request up to 20 s — check this against Vercel function max-duration for the proxy route (Vercel limits not verified here). ([Vercel](https://electric.ax/docs/sync/integrations/vercel); [Troubleshooting → Vercel CDN caching](https://electric.ax/docs/sync/guides/troubleshooting); [Config](https://electric.ax/docs/sync/api/config))

## 5. Auth / security

- **Public by default.** "Electric then exposes access to **any data** that its database user can access in Postgres to **any client** that can connect to the Electric HTTP API. … you **must** secure access to the Electric HTTP API." Layers: API token, network rules, authorizing proxy. ([Security](https://electric.ax/docs/sync/guides/security))
- **`ELECTRIC_SECRET`** — required unless `ELECTRIC_INSECURE=true`; sent as `secret` query param; "The token should _not_ be sent from the client … it should be added by the authorizing proxy". Secure-mode auth bypass via path normalization was fixed in 1.7.12 (2026-08-21). ([Config](https://electric.ax/docs/sync/api/config); [Security](https://electric.ax/docs/sync/guides/security); [CHANGELOG](https://raw.githubusercontent.com/electric-sql/electric/main/packages/sync-service/CHANGELOG.md))
- **Proxy auth (documented primary pattern)** — "Electric is designed to run behind an authorizing proxy". Doc example is literally a Next.js-style route handler: `export async function GET(request: Request)` that copies only `ELECTRIC_PROTOCOL_QUERY_PARAMS` through, sets `table` server-side, loads the user from `Authorization`, and for non-admins does `originUrl.searchParams.set('where', 'org_id = $1'); originUrl.searchParams.set('params[1]', user.org_id)`, appends `secret`, then streams `response.body` back (deleting `content-encoding`/`content-length`). The repo's `examples/proxy-auth/app/shape-proxy/route.ts` is exactly this on Next 14.2.5 and also sets `Vary: Authorization`. **So yes: a Next.js route handler on Vercel can inject a per-user WHERE.** ([Auth guide](https://electric.ax/docs/sync/guides/auth); [proxy-auth route.ts](https://github.com/electric-sql/electric/blob/main/examples/proxy-auth/app/shape-proxy/route.ts))
- **Gatekeeper** — `POST /gatekeeper/:table` issues a shape-scoped JWT; a thin proxy (Caddy/edge) validates the token's shape claim against request params. Suited to edge deployments; `examples/gatekeeper-auth`. ([Auth guide](https://electric.ax/docs/sync/guides/auth))
- **Row-level access** — Docs explicitly avoid DB rules: Electric "deliberately avoids codifying authorization logic into database rules"; the WHERE injected by the proxy *is* the row filter. Our `EXISTS (SELECT 1 FROM meeting_participants …)` rule must be rewritten as `id IN (SELECT meeting_id FROM meeting_participants WHERE user_id = $1)` (the only supported sublink form); EXISTS is rejected by the parser. Where no subquery form fits, the documented alternative is denormalising a tenant/owner column onto each synced table (security guide's `tenant_id` example; issue #3533 comment: "it's mandatory to have a `tenant_id` column on each table to benefit from subqueries"). One shape per (user × table) is the natural consequence; shapes with `field = const` / `field IN (subquery)` are in the "optimized" class. ([Auth guide](https://electric.ax/docs/sync/guides/auth); [Security](https://electric.ax/docs/sync/guides/security); [parser.ex](https://github.com/electric-sql/electric/blob/main/packages/sync-service/lib/electric/replication/eval/parser.ex); [#3533](https://github.com/electric-sql/electric/issues/3533))
- **Column exposure** — `columns` restricts synced columns, but advisory GHSA-c82q-v86f-c87f (low, 2026-06-10): "Excluded columns can be inferred via subset where clauses" → use `queryable_columns`. Critical advisory GHSA-h5rg-pxx7-r2hj (2026-04-14): SQL injection via `ORDER BY` in subset requests (fixed). ([Advisories](https://github.com/electric-sql/electric/security/advisories))

## 6. Write path

- "Electric does read-path sync. It syncs data out-of Postgres, into local apps and services. Electric does not do write-path sync." ([Writes guide](https://electric.ax/docs/sync/guides/writes))
- Four documented patterns (`examples/write-patterns`): **Online writes** (call your API; UI updates when the change syncs back — "best for read-heavy dashboards"); **Optimistic state** (React `useOptimistic`, discard when synced row arrives); **Shared persistent optimistic state** (Valtio + localStorage; separates immutable synced state from mutable local state); **Through-the-DB sync** (PGlite with shadow tables/`INSTEAD OF` triggers/change log). ([Writes guide](https://electric.ax/docs/sync/guides/writes))
- **txid reconciliation** — Backend runs, *inside the same transaction as the mutation*, `SELECT pg_current_xact_id()::xid::text AS txid` ("The `::xid` cast strips off the epoch, giving you the raw 32-bit value that matches what PostgreSQL sends in logical replication streams") and returns it; client `collection.utils.awaitTxId(txid, timeout?)` (default 5 s) or the mutation handler returns `{ txid }`. "ORMs do not return `pg_current_xact_id()` by default. Add a raw SQL query for txid within the same transaction. Without it, optimistic state may drop before the synced version arrives, causing UI flicker." Drizzle example in repo: `tx.execute(sql\`SELECT pg_current_xact_id()::xid::text as txid\`)` inside `db.transaction` (tRPC starter). Alternatives: `awaitMatch()` predicate on the stream, or a crude timeout. ([TanStack DB electric-collection](https://tanstack.com/db/latest/docs/collections/electric-collection); [AGENTS.md](https://github.com/electric-sql/electric/blob/main/AGENTS.md); [electric-orm skill](https://github.com/electric-sql/electric/blob/main/packages/typescript-client/skills/electric-orm/SKILL.md); [tanstack-db-web-starter trpc.ts](https://github.com/electric-sql/electric/blob/main/examples/tanstack-db-web-starter/src/lib/trpc.ts))
- Implication for us: every tRPC mutation that should feel instant must open a Drizzle transaction and return the txid; today's mutation hooks/CRUD chokepoint would need that added.

## 8. Type support & gotchas

- **Client default parsing**: `int2/int4/float4/float8 → number`, `int8 → BigInt`, `bool → boolean`, `json/jsonb → JSON.parse`, arrays → JS arrays (nested OK). "all other types arrive as strings" — timestamps, `numeric`, `uuid`, `interval`, **enums**, custom/domain types. Supply `parser: { timestamptz: s => new Date(s), numeric: parseFloat, … }`. ([TS client](https://electric.ax/docs/sync/api/clients/typescript); [type-parsers.md](https://github.com/electric-sql/electric/blob/main/packages/typescript-client/skills/electric-shapes/references/type-parsers.md))
- **Enums**: synced fine as strings; in WHERE require `status::text IN ('active','done')` (uncast enum comparisons rejected; #1709). ([Shapes guide](https://electric.ax/docs/sync/guides/shapes); [where-clause.md](https://github.com/electric-sql/electric/blob/main/packages/typescript-client/skills/electric-shapes/references/where-clause.md))
- **JSONB**: synced and parsed; **cannot filter on it** (no `->>`, `@>`, `#>>` in WHERE; #2522 open since 2025-04 with active demand for JSONB "extra fields" filtering). ([#2522](https://github.com/electric-sql/electric/issues/2522))
- **Timestamps**: strings; `timetz` unsupported in WHERE. **Arrays**: supported incl. `@> <@ &&`; escaped-backslash decoding bug #3708 open.
- **Booleans**: `"t"/"f"` on the replication path vs `"true"/"false"` on snapshot/subset paths (#4068, open) — matters for non-official clients / raw HTTP consumers.
- **Column naming**: WHERE uses DB column names; client column-mapping exists; snake_case↔camelCase mismatch is the top "validation error" in troubleshooting. ([Troubleshooting → Data & Types](https://electric.ax/docs/sync/guides/troubleshooting))
- **No dedicated "limitations" page** — `/docs/reference/limitations` returns 404 on both domains; limitations are scattered across shapes/troubleshooting.

## 10. Honest fit assessment

Electric would replace exactly one thing: the *transport* by which raw rows of a single table, filtered by a WHERE clause that Electric can parse, reach the browser and stay current — i.e. it could stand in for the Ably `meeting:{id}` ping plus a React Query refetch, and it would give us a durable, CDN-cacheable, resumable log per shape with 409-driven resync. It would **not** replace our tRPC read model: our procedures return joined/derived shapes (meeting + participants + customer + proposal fields) with visibility compiled from CASL into Drizzle `WHERE … EXISTS(...)`; Electric shapes are strictly single-table, reject `EXISTS`, JSONB operators and uncast enums, and only accept `col IN (SELECT …)` — so every visibility rule would have to be re-expressed per table as an `IN (SELECT …)` or a denormalised `visible_to`/owner column, every derived value would move client-side (TanStack DB live queries) or into snapshot tables, and every mutation would need to return a `pg_current_xact_id()` from inside its transaction to avoid optimistic-state flicker. Operationally it adds a stateful Elixir service with a persistent NVMe disk on a non-Vercel host, a direct non-pooled Neon connection with logical replication enabled (irreversible, keeps the 0.25–2 CU compute permanently awake, 40-hour inactive-slot auto-drop, WAL retention caps), table-ownership or DBA-managed publications, 409 full resyncs on every column add/rename via `drizzle-kit push`, and a Vercel route-handler proxy that must disable CDN caching and tolerate 20-second long-polls. On top of that, the vendor has just been absorbed into Databricks with its hosted product shut down, the Postgres-sync roadmap unstated, no maintainer answer on #4770, and the official Next.js example deleted. For "two agents in two browsers on the same meeting see each other's DB changes", Electric is a large architectural pivot (read model, auth model, write model, infra) to gain a generic table-sync primitive we would still have to compose into our entity views; a narrow invalidation signal (Ably/Postgres-notify → React Query `invalidateQueries` on the existing tRPC procedures) keeps the CASL-compiled reads and joined shapes intact and is the cheaper path unless the product goal is genuinely local-first/offline data, which nothing in the brief indicates.
