# Meeting-flow keyboard & focus system — research note

**Date:** 2026-09-13 · **Scope:** one flow-level key map for `/dashboard/meetings/[id]?step=n` (`src/features/meeting-flow/ui/views/meeting-flow.tsx`): ←/→ step, ↑/↓ + A/Z within a step (snap presentation or plain page), 1–7 jump, Escape (overlay first, then present mode), P toggles present mode — without hijacking typing or an open Radix layer · **Stack (installed):** Next 15.5.9, React/react-dom 19.2.4, nuqs 2.8.8, `radix-ui` 1.4.3 with `@radix-ui/react-dialog` 1.1.15 / `react-select` 2.2.6 / `react-dropdown-menu` 2.1.16 / `react-menu` 2.1.16 / `react-dismissable-layer` 1.1.11 / `react-roving-focus` 1.1.11 / `react-focus-scope` 1.1.7 / `react-use-escape-keydown` 1.1.1, `motion` 12.31.0 (framer-motion 12.31.0, motion-dom 12.30.1), Tailwind v4 (`package.json`, `node_modules/.pnpm`).

## Summary

One `keydown` listener on **`window`, bubble phase**, mounted by `MeetingFlowViewInner`. That position is *after* every Radix handler by construction: Radix's Escape handling is a `document` **capture** listener that calls `preventDefault()` when it dismisses; Select/Menu/RovingFocus arrow handling is React `onKeyDown`, and Next 15 hydrates `document`, so React's delegated handlers also run at `document` — window-bubble is the last stop in the path. So `event.defaultPrevented` is a complete "Radix consumed this key" signal for Escape, arrows, Home/End, PageUp/Down and Tab. It is **not** a signal for single-character keys (Select/Menu typeahead never prevents them), so pair it with a target guard: skip when the target is a typing element or when the target is *outside the flow root* (every Radix layer is portaled to `<body>`, and focus is trapped/kept inside an open layer). Escape then sequences itself: an open Sheet/Dialog/Select/Menu/Tooltip eats it, the next Escape exits present mode. After a step change, move focus to the step root (`tabIndex={-1}` region for page steps; the existing `role="region" tabIndex={0}` scroller for the presentation) with `focus({ preventScroll: true })` in a `useEffect` keyed on the step — nuqs updates React state synchronously, so the effect runs on the new step's commit. Browser arrow/PageDown scrolling then targets that scroller (Chromium starts its scroll chain at the focused element). For ↑/↓/A/Z inside the presentation, compute the target section index from state and call `scroller.scrollTo({ top })` (absolute scroll → snaps to the nearest position regardless of direction; unaffected by `scroll-snap-stop`; honours `scroll-behavior`), rather than relying on native directional scrolling or `scrollBy` (Safari ignores snap for `scrollBy`). Expose the map with `aria-keyshortcuts` on the controls each key drives plus a visible hint/help dialog; single-letter keys are WCAG 2.1.4-compliant only because they are focus-scoped to the flow region.

## 1. Event routing, phases, and the Radix `defaultPrevented` contract

### 1.1 Platform facts

- `keydown` bubbles, is cancelable, and its target "is the currently focused element processing keyboard activity … If no suitable element is focused, the target is `<body>` or the root"; the event "bubbles and can reach `Document` and `Window`" ([MDN keydown](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)). UI Events: keydown is "Cancelable: Yes", default actions "Varies: beforeinput and input events; launch text composition system; blur and focus events; keypress event (if supported); activation behavior; other event", and "If this event is canceled, the associated event types MUST NOT be dispatched, and the associated actions MUST NOT be performed" ([UI Events §keydown](https://w3c.github.io/uievents/#event-type-keydown)). Native arrow-key scrolling is one of those "other" default actions, which is why Radix and our handler call `preventDefault()` on keys they consume.
- Window is in the propagation path: "A document's get the parent algorithm, given an event, returns null if event's type attribute value is "load" or document does not have a browsing context; otherwise the document's relevant global object" ([DOM §get the parent](https://dom.spec.whatwg.org/#get-the-parent)). At each node, "Let listeners be a clone of event's currentTarget attribute value's event listener list" and listeners are stored in insertion order ("append listener to eventTarget's event listener list") ([DOM §invoke](https://dom.spec.whatwg.org/#concept-event-listener-invoke), [§add an event listener](https://dom.spec.whatwg.org/#add-an-event-listener)). So same-target, same-phase listeners run in registration order; a listener on `window` (bubble) runs after everything registered on `document`, whatever its registration time.
- `Event.defaultPrevented` "returns a boolean value indicating whether or not the call to `Event.preventDefault()` canceled the event" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Event/defaultPrevented)); it stays true for every later listener in the path.

### 1.2 Where React's handlers actually live in this app

- Since React 17, "React will no longer attach event handlers at the `document` level. Instead, it will attach them to the root DOM container into which your React tree is rendered"; capture-phase React handlers "employ actual browser capture listeners" ([React 17 RC blog](https://legacy.reactjs.org/blog/2020/08/10/react-v17-rc.html)). React 19's `listenToAllSupportedEvents(rootContainerElement)` registers `listenToNativeEvent(domEventName, false|true, rootContainerElement)` for every delegated event (`node_modules/react-dom/cjs/react-dom-client.development.js:19209`).
- Next 15 App Router hydrates the whole document: `const appElement = document;` … `hydrateRoot(appElement, reactEl, …)` (`node_modules/next/dist/client/app-index.js:30,224`). Therefore React's synthetic `onKeyDown` handlers (Radix Select/Menu/RovingFocus included) run from a native **bubble listener on `document`**, and `onKeyDownCapture` handlers from a native **capture listener on `document`** — both registered at hydration, i.e. before any hook we mount. React exposes capture variants as the `Capture` suffix ([react.dev common props](https://react.dev/reference/react-dom/components/common)).

None of these call `stopPropagation()` on keydown (grep of the Select/Menu/Dialog/Popover/RovingFocus builds found `preventDefault` only), so a window listener always receives the event. The repo's `dialog.tsx` only patches `stopPropagation` for clicks. The repo's own `carousel.tsx` follows the same contract: `onKeyDownCapture` with `event.preventDefault()` for `ArrowLeft/ArrowRight` on a `role="region" aria-roledescription="carousel"` box (`src/shared/components/ui/carousel.tsx:82-131`).

**Consequence.** With a window-bubble listener, `event.defaultPrevented === true` iff a Radix (or carousel/slider) handler consumed the key, for every non-character key we care about. The only Radix key that reaches us un-prevented is a single printable character typed into an open Select/Menu (typeahead) or into any text field — hence the guard in §2.

**Anti-pattern.** Do not register on `document` with `{ capture: true }`: it would run *before* Radix's capture listener (registered later, at layer mount), see `defaultPrevented === false`, exit present mode **and** let Radix close the dialog on the same Escape. A `document` bubble listener registered at flow mount also runs after React's `document` bubble listener only because it was added later; window-bubble does not depend on registration order.

### 1.4 Detecting "a Radix layer is open"

- `DismissableLayerContext` is module-private; the package exports only `DismissableLayer`, `DismissableLayerBranch`, `Root`, `Branch` (`react-dismissable-layer/dist/index.mjs`, bottom). There is no public "layer stack" API.
- **Target ancestry (recommended).** Every content part is rendered through a Portal into `document.body` (Radix docs: `Select.Portal` "portals the content part into the body" — [radix-ui.com/primitives/docs/components/select](https://www.radix-ui.com/primitives/docs/components/select)), so an open layer's DOM is *outside* the flow root. Modal Dialog/Select/Menu use `FocusScope trapped` (focus is pulled back inside on `focusin` outside), and the non-modal Popover dismisses on focus-outside (`PopoverContentNonModal.onInteractOutside` only prevents when the target is the trigger). Hence "focus is inside an open layer" ⇔ `!flowRoot.contains(event.target)`. Treat `event.target === document.body` (nothing focused) as inside.
- **Modal signals (belt-and-braces).** Modal Dialog, Select and DropdownMenu (`modal = true` defaults in `react-dialog` and `react-dropdown-menu`; Popover `modal = false`) wrap content in `RemoveScroll`, whose `useLockAttribute` sets `document.body.setAttribute('data-scroll-locked', n)` (`react-remove-scroll-bar/dist/es2015/component.js:6,28`), and call `hideOthers(content)`, which marks every other child of `document.body` with `aria-hidden="true"` and `data-aria-hidden="true"` (`aria-hidden/dist/es2015/index.js:124-134`; default parent `ownerDocument.body`). So `document.body.hasAttribute('data-scroll-locked')` or `flowRoot.closest('[data-aria-hidden="true"]')` ⇒ a modal layer is open. Both are implementation details of Radix's dependencies, not API.
- **DOM markers.** Content carries `data-state="open" | "closed"` (Dialog/Popover/Select/Menu content and their triggers; Radix docs list `[data-state]` on Content/Trigger — [dialog](https://www.radix-ui.com/primitives/docs/components/dialog), [popover](https://www.radix-ui.com/primitives/docs/components/popover)); Select trigger has `role="combobox" aria-expanded aria-controls`; Menu content has `data-radix-menu-content`; every Popper-positioned layer (Select in `position="popper"`, Menu, Popover, Tooltip, HoverCard) sits in a `div[data-radix-popper-content-wrapper]` (`react-popper/dist/index.mjs:147`). A `document.querySelector('[role="dialog"][data-state="open"], [role="listbox"][data-state="open"], [data-radix-menu-content][data-state="open"]')` works but enumerates primitives; the popper wrapper also matches hover-only Tooltips/HoverCards. Prefer target ancestry + `defaultPrevented`.

## 2. Typing-target guard and modifier keys

- **Typing targets.** MDN's keydown target list (`<input>`, `<textarea>`, `contentEditable`) plus the roles whose APG keyboard interaction consumes the same keys: combobox ("Down Arrow: If the popup is available, moves focus into the popup … Escape: Dismisses the popup"; popup listbox "Down Arrow: Moves focus to and selects the next option") ([APG combobox](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/)); listbox/option ("Down Arrow: Moves focus to the next option … Type a character: focus moves to the next item") ([APG listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/)); slider ("Right Arrow / Up Arrow: Increase the value … Home / End / Page Up / Page Down") ([APG slider](https://www.w3.org/WAI/ARIA/apg/patterns/slider/)); menu/menuitem ("Down Arrow … Up Arrow … Printable Characters: optionally moves focus … Escape: Close the menu that contains focus and return focus") ([APG menu](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/)). Guard: `target.closest('input, textarea, select, [contenteditable=""], [contenteditable="true"], [role="combobox"], [role="listbox"], [role="option"], [role="textbox"], [role="searchbox"], [role="slider"], [role="spinbutton"], [role="menu"], [role="menuitem"], [role="menuitemcheckbox"], [role="menuitemradio"]')` or `target.isContentEditable`. cmdk's Command input is `role="combobox"` and its list `role="listbox"` (`cmdk/dist/index.mjs`), so the same guard covers the command palette. The existing `useToolbarShortcuts` guard (`src/shared/components/query-toolbar/hooks/use-toolbar-shortcuts.ts:39-51`) checks tag name + `isContentEditable` only; extend it rather than fork it.
- **IME.** "Since Firefox 65, keydown events fire during Input Method Editor (IME) composition"; guard `if (event.isComposing || event.keyCode === 229) return` ([MDN keydown](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)). Chromium likewise skips default navigation for the process key (`keyboard_event_manager.cc` "Do not perform the default action when inside a IME composition context").
- **Key values.** `event.key` is the produced character/named key: `"Escape"`, `"ArrowUp"…`, `"PageUp"`, `"Home"`, digits `"0"–"9"`; the numpad "generates events with the key value of "0"" etc., distinguishable only by `event.code` (`Digit1` vs `Numpad1`); `Shift+2` yields `"@"` on US layouts ([MDN key values](https://developer.mozilla.org/en-US/docs/Web/API/UI_Events/Keyboard_event_key_values)). Match digits on `event.key` (`'1'`–`'7'`, bounded by `TOTAL_STEPS`) so both digit rows work; match letters on `event.key.toLowerCase()`.
- **Modifiers.** APG: avoid "Any modifier keys + any of Tab, Enter, Space, or Escape", "Meta key + any other single key", "Alt + a function key", and AT conflicts "Caps Lock + …, Insert + …, Scroll Lock + …, macOS only: Control + Option + …" ([APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)). Radix's own rule for arrows is `if (event.metaKey || event.ctrlKey || event.altKey || event.shiftKey) return` (RovingFocusGroupItem). Recommendation: bail on `metaKey || ctrlKey || altKey` for every key (Cmd/Ctrl+←/→ are browser history/line-edit gestures; Alt+letter produces a different `key` on macOS anyway); additionally bail on `shiftKey` for **arrows** (mirrors Radix; Shift+Arrow is selection/skip in widgets) but **not** for letters or digits: the ARIA spec warns "in French keyboard layouts, the number characters are not available until you press the Control key" and that authors "can prevent conflicts by avoiding keys other than ASCII letters, as number characters and common punctuation often require modifiers" ([WAI-ARIA 1.2 aria-keyshortcuts](https://www.w3.org/TR/wai-aria-1.2/#aria-keyshortcuts)) — so treat the digit jump as best-effort on non-US layouts, never as the only path.
- **Auto-repeat.** `KeyboardEvent.repeat` is "true if the given key is being held down such that it is automatically repeating" ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/repeat)); UI Events sets it "when key is depressed for a sustained period" ([UI Events](https://w3c.github.io/uievents/#event-type-keydown)). Ignore repeats for P/Escape/digits (toggles must not flap); allow them for arrows/A/Z if you want hold-to-scroll, but then compute targets from a pending index (§4.3).
- **WCAG 2.1.4 Character Key Shortcuts.** A shortcut "implemented using only letter …, punctuation, number, or symbol characters" must satisfy one of: "A mechanism is available to turn the shortcut off", "remap the shortcut to include one or more non-printable keyboard keys", or "The keyboard shortcut for a user interface component is only active when that component has focus"; single-key shortcuts "are disastrous for speech users"; focus-scoped shortcuts (e.g. "listboxes and drop-down menus") are the accepted path ([Understanding 2.1.4](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html)). P, A, Z and 1–7 are character keys; ←/→/↑/↓/Escape are not. The target-ancestry guard (§1.4) makes the character keys active only while focus is inside the flow region (or on `body` with nothing focused — see §3 for why we always leave focus inside the region), which is what the SC asks for; a preferences toggle ("turn off") is the alternative if the region ever loses that guarantee.
- **Screen readers.** ARIA: "Some user agents and assistive technologies have a browse mode where standard input events, such as up and down arrow key events, are intercepted and used to control a reading cursor. This browse mode behavior prevents elements that do not have a widget role from receiving and using such keyboard and gesture events" ([WAI-ARIA 1.2 application role](https://www.w3.org/TR/wai-aria-1.2/#application)). A `role="region"` step root is not a widget, so SR users in browse mode will not trigger the arrow/letter map — they navigate with the visible Prev/Next/StepNav buttons instead. Do **not** reach for `role="application"` to force it; it disables browse-mode reading of the presentation copy.

## 3. Focus after a step change (nuqs → effect → `focus({ preventScroll })`)

- **nuqs timing.** `useQueryState` is `useQueryStates` under the hood; its setter runs `emitter.emit(urlKey, { state, query })` synchronously, which the hook's own subscription turns into `setInternalState(...)` (`node_modules/nuqs/dist/index.js:484-553`); the URL write is queued (`globalThrottleQueue.push` + `flush`) with a default throttle of 50 ms (Safari: 120 ms on ≥17, 320 ms before) (`debounce-*.js:5-11`), then applied by `history.replaceState`/`pushState` inside `startTransition` (`impl.app-*.js:41-56`). Defaults: `history = "replace"`, `scroll = false`, `shallow = true`, `clearOnDefault = true` (`index.js:454`). Docs: "the React state remains responsive by reflecting changes instantly" and updates are batched; the setter "return[s] a Promise that resolves to the updated URLSearchParams" ([nuqs README via Context7](https://github.com/47ng/nuqs)). So `setCurrentStep(n)` re-renders the new step in the same React update; a `useEffect(() => root.focus({ preventScroll: true }), [currentStep])` fires after that commit — no `flushSync` and no awaiting the URL promise. React: `useEffect` runs after commit and does not block paint; `useLayoutEffect` "fires synchronously after all DOM mutations … before the browser paints" ([react.dev useLayoutEffect](https://react.dev/reference/react/useLayoutEffect)) — use it only if a one-frame focus-ring flash is observed. `history: 'push'` per step is a product choice (Back = previous step); keep `replace` unless asked.
- **`focus()` scrolls by default — to centre.** HTML: "If options["preventScroll"] is false, then scroll a target into view given this, "auto", "center", and "center"" ([HTML §focus()](https://html.spec.whatwg.org/multipage/interaction.html#dom-focus)); "By default, this method also scrolls element into view. Providing the preventScroll option and setting it to true prevents this behavior" (same). In a `y mandatory` container that is an *absolute* scroll (§4.1), so a bare `focus()` on a section would centre-then-re-snap. Always pass `{ preventScroll: true }` when focusing a step root that sits inside (or is) a snap scroller. Support: `preventScroll` Chrome 64, Firefox 68, Safari 15 / iOS 15.5; `focusVisible` Chrome 145, Firefox 104, Safari 18.4 ([BCD `api/HTMLElement.json`](https://github.com/mdn/browser-compat-data/blob/main/api/HTMLElement.json)).
- **`tabIndex={-1}`.** "If the value is a negative integer: The user agent must consider the element as a focusable area, but should omit the element from any tabindex-ordered focus navigation scope" ([HTML §tabindex](https://html.spec.whatwg.org/multipage/interaction.html#the-tabindex-attribute)); APG: "`tabindex="-1"` — The element is not included in the tab sequence but is focusable with element.focus()" ([APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)). Sequential Tab after that continues from the focused element (the spec's "sequential focus navigation starting point"/focused-area rules, [HTML §sequential focus](https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation)).
- **Which scroller do native arrows/PageDown scroll?** Chromium: `ScrollManager::LogicalScroll` starts with `node = start_node; if (!node) node = frame_->GetDocument()->FocusedElement(); if (!node) node = mouse_press_node;` then walks `RecomputeScrollChain(*node, direction)`; the arrow handler calls `BubblingScroll(direction, granularity, nullptr, possible_focused_node, true)` ([scroll_manager.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/input/scroll_manager.cc), [keyboard_event_manager.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/input/keyboard_event_manager.cc)). I.e. focus inside the presentation scroller ⇒ ↑/↓/PageDown/Space scroll *that* scroller. Chrome 132+ also makes scrollers with no focusable children keyboard-focusable by default, and recommends `tabindex="0"` when you want the scroller itself focusable ([Chrome blog](https://developer.chrome.com/blog/keyboard-focusable-scrollers)). The presentation scroller already has `role="region" tabIndex={0} aria-label` (`snap-presentation.tsx:68-69`); the page-step scroller (`meeting-flow.tsx:225`, `div.min-h-0.flex-1.overflow-y-auto`) has neither — give it (or a step-root wrapper inside it) `tabIndex={-1}` so it can receive focus. Firefox/WebKit start-node rules were not read from source (Unverified), but WPT `css/css-scroll-snap/input/keyboard.html` focuses the scroller and asserts arrow snapping in all three engines (§4.2), which is the behaviour we rely on.
- **What APG says about wizards and carousels.** There is no wizard/stepper/presentation pattern in APG (patterns index lists Accordion … Window Splitter; none named wizard, stepper or slideshow — [APG patterns](https://www.w3.org/WAI/ARIA/apg/patterns/)). The closest analogues:
  - *Tabs* — "Left Arrow: moves focus to the previous tab … Right Arrow: Moves focus to the next tab", "It is recommended that tabs activate automatically when they receive focus as long as their associated tab panels are displayed without noticeable latency", and "When the tabpanel does not contain any focusable elements or the first element with content is not focusable, the tabpanel should set `tabindex="0"`" ([APG tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)). The APG's caveat that selection-follows-focus is harmful when "displaying a new panel causes a network request" does not apply: a step change is a shallow, client-only URL update.
  - *Carousel* — container "region or group" with `aria-roledescription="carousel"` and a label; each slide `role="group"` + `aria-roledescription="slide"`; optional live-region wrapper "`polite`: if the carousel is NOT automatically rotating" with `aria-atomic="false"`; "Activating the rotation control, next slide, and previous slide buttons do not move focus"; the pattern relies on Tab + buttons, "Arrow keys for slide navigation are not mentioned" ([APG carousel](https://www.w3.org/WAI/ARIA/apg/patterns/carousel/)). The repo's `carousel.tsx` already implements this shape.
  - *Region* — "Authors MUST give each element with role region a brief label … SHOULD reference a visible label with aria-labelledby … SHOULD include the label inside of a heading whenever possible"; "Assistive technologies SHOULD enable users to quickly navigate to elements with role region" ([WAI-ARIA 1.2 region](https://www.w3.org/TR/wai-aria-1.2/#region)).
  - APG on roving tabindex: "One benefit of using roving `tabindex` rather than `aria-activedescendant` to manage focus is that the user agent will scroll the newly focused element into view" ([APG keyboard interface](https://www.w3.org/WAI/ARIA/apg/practices/keyboard-interface/)) — the same mechanism we suppress with `preventScroll` because snap already positions the section.
- **Scroller vs heading.** Focus the **step root region** (page steps: a new `div role="region" tabIndex={-1} aria-labelledby={h1Id}` inside the shared scroller; presentation step: the existing scroller, which is already the region) — not the `<h1>`: (a) the region's accessible name *is* the step title, so the announcement is the same; (b) the focused node must be inside the scroller for native arrow keys to reach it (Chromium chain above); (c) headings with `tabIndex=-1` get read once and leave the user with no landmark to return to. Announce progress separately with a polite live region that exists before it changes: "The `aria-live` attribute should be set on an empty element before any content updates occur"; `polite` = "presented at the next graceful opportunity" ([MDN aria-live](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-live)). The footer's `{currentStep} / {TOTAL_STEPS}` span (`meeting-flow.tsx:283-285`) is the natural host: `aria-live="polite" aria-atomic="true"` with text "Step 2 of 7: Which Specialties Matter to You". Note `hideOthers` deliberately skips `[aria-live]` elements (`aria-hidden/dist/es2015/index.js:131-133`), so it keeps working while a modal is open.
- Present-mode state: keep it in the URL next to `step` (`parseAsBoolean` `present`) so a reload during a meeting restores the mode, or in `useState` if it must never be shareable; either way it is orthogonal to focus.

## 4. Programmatic vs native scrolling inside the mandatory snap container

### 4.1 Spec semantics that decide the API

- Absolute scrolls: "programmatically scrolling via APIs such as `scrollTo()`", "tabbing through the document's focusable elements", "homing operations such as the Home/End keys" — "Scroll snapping responds to an absolute scroll by finding the nearest valid snap position, regardless of direction". Relative scrolls with direction and end position: "programmatically scrolling via APIs such as `scrollBy()`", "paging operations such as the PgUp/PgDn keys"; with direction only: "pressing an arrow key on the keyboard" — "Scroll snapping responds to a relative scroll by finding the nearest valid snap position in the intended direction (if possible)" ([css-scroll-snap-1 §6.1](https://drafts.csswg.org/css-scroll-snap-1/#scroll-types)).
- `scroll-snap-stop: always` — "The scroll container must not pass over a snap position defined by this element during the execution of a scrolling operation; it must instead snap to the first of this element's snap positions" and "This property has no effect on non-relative scrolling operations, as they do not conceptually "pass over" any snap positions" ([§5.3](https://drafts.csswg.org/css-scroll-snap-1/#scroll-snap-stop)). So `snap-always` bounds wheel/touch/arrow/PgDn, never `scrollTo`/`scrollIntoView`.
- Target of `scrollIntoView()`: "the user agent must snap to one of that element's snap positions if its nearest scroll container is a scroll snap container" ([§6.2](https://drafts.csswg.org/css-scroll-snap-1/#choosing)); "the UA should use the element's scroll snap area, rather than just its border box, to determine which area of the scrollable overflow area to bring into view, even when snapping is off" ([§5.1](https://drafts.csswg.org/css-scroll-snap-1/#scroll-margin)). Paging: "If a scroll by page operation (e.g. Page down / Page up) is being performed, eligible snap positions that require scrolling less than or equal to the size of the optimal viewing region of the scroll container should be selected before any farther away, ignoring the starting snap positions so that progress is still made in the intended direction" ([§6.2](https://drafts.csswg.org/css-scroll-snap-1/#choosing)). The selection algorithm as a whole "is intentionally left mostly undefined" ([§6](https://drafts.csswg.org/css-scroll-snap-1/#snap-mechanics)) — "exactly one snap point per arrow press" is a UA behaviour verified by test (§4.2), not a normative guarantee.
- CSSOM View `scrollIntoView(options)`: defaults `behavior "auto"`, `block "start"`, `inline "nearest"`, `container` null; "If the container dictionary member of options is "nearest", set container to the element"; "scroll a target into view" runs "For each ancestor element or viewport that establishes a scrolling box … in order of innermost to outermost", scrolling each whose target position differs "or scrolling box has an ongoing smooth scroll", and stops after `container` ([CSSOM View §scrollIntoView](https://drafts.csswg.org/cssom-view/#dom-element-scrollintoview), [§scroll a target into view](https://drafts.csswg.org/cssom-view/#scroll-a-target-into-view)). The spec's own carousel example comments: "scrollIntoView correctly aligns target item respecting scroll-snap-align, scroll-margin, and the scroll container's scroll-padding" and passes `container: 'nearest', behavior: 'smooth'`. "Perform a scroll": "Abort any ongoing smooth scroll for box … If … behavior is "auto" and element is not null and its computed value of the scroll-behavior property is smooth, or behavior is smooth then perform a smooth scroll … otherwise, perform an instant scroll" ([§perform a scroll](https://drafts.csswg.org/cssom-view/#perform-a-scroll)). MDN confirms `behavior: "auto"` on both `scrollIntoView` and `scrollTo` "is determined by the computed value of the scroll-behavior CSS property" ([MDN scrollIntoView](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollIntoView), [MDN scrollTo](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollTo)) — closing the prior note's open item.
- Support ([BCD `api/Element.json`](https://github.com/mdn/browser-compat-data/blob/main/api/Element.json)): `scrollIntoView` options object Chrome 61 / Firefox 36 / Safari 14 ("Before Safari 15.4, there was no support for the `smooth` behavior", "No support for `center` option"); `scrollTo`/`scrollBy` options with `behavior` Chrome 61 / Firefox 36 / Safari 14; scroll methods return a Promise only in Chrome 150+. The `container` member has no BCD entry (Unverified). `scroll-snap-stop`: Chrome 75, Firefox 103, Safari 15 ([BCD css/properties/scroll-snap-stop.json](https://github.com/mdn/browser-compat-data/blob/main/css/properties/scroll-snap-stop.json)).
- Reduced motion: `motion-safe:scroll-smooth` (prior note) makes `scrollTo` instant under `prefers-reduced-motion: reduce`. Motion's `useReducedMotion()` reads `prefersReducedMotion.current`, which is `null` server-side ("Does this device prefer reduced motion? Returns `null` server-side." — `motion-dom/dist/es/render/utils/reduced-motion/state.mjs`) and is captured once via `const [shouldReduceMotion] = useState(prefersReducedMotion.current)` with a `TODO See if people miss automatically updating` (`framer-motion/dist/es/utils/reduced-motion/use-reduced-motion.mjs`) — ⚠️ the docs' "It will actively respond to changes and re-render your components" ([motion.dev](https://motion.dev/docs/react-use-reduced-motion)) is not what 12.31.0 does; `MotionConfig reducedMotion="user"` goes through the same hook (`use-reduced-motion-config.mjs`). Prefer the CSS media query (`motion-safe:`) for scroll behaviour; do not gate scrolling on the hook.

### 4.2 Engine evidence

- WPT `css/css-scroll-snap/input/keyboard.html` (scroller with `tabindex="0"`, `y mandatory`) asserts "Snaps to bottom-left after pressing ArrowDown" (`scrollTop` 0 → 400, with `assert_greater_than(scrollCounter.count, 1)` — i.e. animated, not a jump), the inverse for ArrowUp, and, with `scroll-snap-stop: always` on a nearer target, "If the original intended offset is valid … but there's a defined snap offset in between, use the defined snap offset" ([test source](https://github.com/web-platform-tests/wpt/blob/master/css/css-scroll-snap/input/keyboard.html)). wpt.fyi stable runs: **8/8 pass in Chrome 153.0.8010.36, Firefox 155.0.1 and Safari 26.6** ([wpt.fyi](https://wpt.fyi/results/css/css-scroll-snap/input/keyboard.html?label=master&label=stable)). `keyboard-snap-interruption.html` ("Interrupting a snap animation with another key press targeting the same node preserves snapping destination", `scroll-behavior: smooth`) passes in Chrome and Firefox and **fails in Safari 26.6** (same API). Chromium implements arrows as `SnapForDirection` and PgUp/PgDn as `SnapForPageScroll` with the comment "Pressing the arrow key is considered as a scroll with intended direction only. Pressing the PgUp/PgDn key is considered as a scroll with intended direction and end position" ([scroll_manager.cc](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/input/scroll_manager.cc)). Chrome's guidance: "Scroll snapping happens after all scroll operations including those initiated by script … the browser will calculate the intended scroll position of the operation, then apply appropriate snapping logic"; Chrome also uses snap/padding "when calculating scroll amount for the Element.scrollIntoView() operation" ([web.dev](https://web.dev/articles/css-scroll-snap)).
- WebKit open bugs that touch this design (all NEW, via [bugs.webkit.org REST](https://bugs.webkit.org/rest/bug/316084)): **316084** "scrollBy doesn't respect scroll-snap and scroll-snap-stop at all" (Safari 26, 2026-06) → never page with `scrollBy`; **242566** "[css-scroll-snap] scroll-snap-stop doesn't work" (Safari 15, trackpad) → `snap-always` is advisory on Safari trackpads even though the keyboard WPT passes; **318525** "Scroll snap doesn't respect scroll-behavior:smooth" and **311356** "Re-snap to a new snap target after layout change ignores scroll-behavior: smooth" (re-snaps caused by style changes jump instantly) → do not implement section navigation by toggling `scroll-snap-align`; **241737** "Small programmatic scrolls with scroll snap don't scroll in WebKit" → always scroll to the exact snap position, never nudge; **253195** momentum disabled in sections taller than the viewport (iOS); **251003** "Scroll-snap snaps to wrong element after VoiceOver navigation"; **323808** "`scroll-margin` is not applied in scroll container coordinate space" → keep `scrollMarginTop: 0` on sections (`snap-section.tsx:48`) and use `scroll-padding` on the scroller (already `scroll-pt-(--pin-h)`). **245722** (smooth `scrollIntoView` on the root `y mandatory` scroller) is RESOLVED FIXED and did not apply to sub-scrollers (prior note).
- Firefox: 1959811 (UNCONFIRMED) "`scroll-behavior: smooth` interacts poorly with `scroll-snap-type: x mandatory` and `scroll-snap-stop: always`, causing scroll to get stuck on some items" ([bugzilla](https://bugzilla.mozilla.org/show_bug.cgi?id=1959811)); 1534520 asks Firefox to honour `scroll-snap-align` for `scrollIntoView` even when `scroll-snap-type: none` (spec "may") — irrelevant with mandatory snap. Bugzilla's HTML search is JS-gated; results came from its REST API.

### 4.3 Verdict for ↑/↓/A/Z in the presentation

1. **Compute the target from state, then absolute-scroll.** `activeIndex` (`useInView … amount: 0.5`, `snap-presentation.tsx:39-45`) plus a `pendingIndexRef` (so a second press during a smooth animation advances from the *pending* target, since "perform a scroll" aborts the ongoing smooth scroll) → `scroller.scrollTo({ top: sections[i].offsetTop - scrollPaddingTop })`. `offsetTop` resolves against the scroller because it is `absolute` (`snap-presentation.tsx:60`) and therefore the sections' offsetParent; subtract the scroller's computed `scroll-padding-top` (the `--pin-h` band below `lg`) so the requested position *is* the snap position — snapping then has nothing to correct and Safari's small-programmatic-scroll bug (241737) cannot bite. This is the same absolute-scroll path the prior note chose for Next/Prev; `snap-always` does not trap it, `motion-safe:scroll-smooth` animates it, `prefers-reduced-motion` makes it instant.
2. `section.scrollIntoView({ block: 'start' })` is spec-equivalent (respects `scroll-padding`, snaps to the section's own snap position) but walks *every* ancestor scrolling box unless `container: 'nearest'` is supported; `overflow: hidden` ancestors count as scrolling boxes, so an ancestor with hidden overflow could shift. Acceptable fallback; not the primary.
3. Do **not** synthesise "native" directional scrolling (`scrollBy`, `scrollTop += n`): WebKit ignores snap for `scrollBy` (316084), and relative scrolls are what `snap-always` and the UA's undefined selection heuristics act on.
4. Leave real ↑/↓/PageDown/Space/Home/End to the browser when the flow handler does not claim them (page steps): with focus inside the scroller they already scroll it and, in the presentation, already snap one section per press in current stable engines (§4.2). Only claim ↑/↓ in the presentation if you want A/Z parity and the pending-index behaviour; otherwise map only A/Z and let native arrows through.

## 5. Exposing the key map

- `aria-keyshortcuts` "Indicates keyboard shortcuts that an author has implemented to activate or give focus to an element"; value is "a space-separated list of keyboard shortcuts … The keys defined in the shortcuts represent the physical keys pressed and not the actual characters generated"; modifiers "exactly according to the UI Events KeyboardEvent key Values spec — "Alt", "Control", "Shift", "Meta", or "AltGraph""; non-modifier names are printable characters or key names such as "Enter", "Tab", "ArrowRight", "PageDown", "Escape"; modifiers first, "a" and "A" equivalent; "If the character used is determined by a modifier key, the author MUST specify the actual key used" (e.g. "Shift+5", not "%") ([WAI-ARIA 1.2](https://www.w3.org/TR/wai-aria-1.2/#aria-keyshortcuts)). MDN: it "has no effect on functionality"; "Include shortcuts in menus and tooltips", provide "a shortcut cheat sheet, or help dialog", "Avoid single-letter shortcuts and common screen reader shortcuts", and disable the attribute together with the control ([MDN aria-keyshortcuts](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-keyshortcuts)). It is a global attribute (all roles).
- Placement follows the semantics ("activate or give focus to an element"): Previous button `aria-keyshortcuts="ArrowLeft"`, Next `"ArrowRight"`, each `StepNav` button its digit (`"1"` … `"7"`), the present-mode toggle `"P"`, the presentation region `"ArrowUp ArrowDown A Z"` only if it owns those keys, and the overlay-panel triggers nothing (Escape closes, it does not open). Announcing exposure does not make a key work; the handler does.
- Visible discovery: reuse the muted-hint pattern already shipped (`KEYBOARD_HINT_TEXT = 'Press / to search · F to filter · ← → to paginate'`, `src/shared/components/query-toolbar/constants/keyboard-hints.ts`) and the `<kbd>` badge in `sidebar-search-bar.tsx`; add a `?` shortcut-help `Dialog` (Radix handles its own Escape, which the flow handler then ignores via `defaultPrevented`). Present mode should show the hint strip briefly on entry, since chrome is hidden.
- SR announcement of the *result* (not the key) is the live region from §3.

## Recommendation

One hook, mounted once in `MeetingFlowViewInner`, plus two small additions: a focusable step root for page steps and a `scrollToIndex` on `PresentationContext`.

```tsx
// src/features/meeting-flow/hooks/use-meeting-flow-keys.ts (sketch — not code to paste)
'use client'
import { useEffect } from 'react'
import { TOTAL_STEPS } from '@/features/meeting-flow/constants/step-config'

const TYPING_SELECTOR = [
  'input', 'textarea', 'select', '[contenteditable=""]', '[contenteditable="true"]',
  '[role="combobox"]', '[role="listbox"]', '[role="option"]', '[role="textbox"]', '[role="searchbox"]',
  '[role="slider"]', '[role="spinbutton"]', '[role="menu"]', '[role="menuitem"]',
  '[role="menuitemcheckbox"]', '[role="menuitemradio"]',
].join(',')

interface Args {
  rootRef: React.RefObject<HTMLElement | null>   // the flow root (header + step + footer), NOT body
  step: number
  setStep: (n: number) => void
  present: boolean
  setPresent: (v: boolean) => void
  /** undefined on page steps → arrows fall through to native scrolling */
  sectionNav?: { next: () => void, prev: () => void }
}

export function useMeetingFlowKeys({ rootRef, step, setStep, present, setPresent, sectionNav }: Args) {
  useEffect(() => {
    function onKeyDown(event: KeyboardEvent) {
      if (event.defaultPrevented) return                       // Radix/carousel/slider consumed it (§1.3)
      if (event.isComposing || event.keyCode === 229) return    // IME (§2)
      if (event.metaKey || event.ctrlKey || event.altKey) return
      const target = event.target
      if (!(target instanceof Element)) return
      const root = rootRef.current
      if (!root) return
      const outsideFlow = target !== document.body && !root.contains(target) // portaled Radix layer has focus (§1.4)
      if (outsideFlow || target.closest(TYPING_SELECTOR) || (target as HTMLElement).isContentEditable) return

      const key = event.key
      if (key === 'Escape') { if (present) { event.preventDefault(); setPresent(false) } return }
      if (event.repeat && !['ArrowUp', 'ArrowDown', 'a', 'z', 'A', 'Z'].includes(key)) return
      if (!event.shiftKey && key === 'ArrowLeft')  { event.preventDefault(); if (step > 1) setStep(step - 1); return }
      if (!event.shiftKey && key === 'ArrowRight') { event.preventDefault(); if (step < TOTAL_STEPS) setStep(step + 1); return }
      if (sectionNav && !event.shiftKey && (key === 'ArrowDown' || key === 'ArrowUp')) {
        event.preventDefault(); (key === 'ArrowDown' ? sectionNav.next : sectionNav.prev)(); return
      }
      if (sectionNav && (key === 'z' || key === 'Z')) { event.preventDefault(); sectionNav.next(); return }
      if (sectionNav && (key === 'a' || key === 'A')) { event.preventDefault(); sectionNav.prev(); return }
      if (key === 'p' || key === 'P') { event.preventDefault(); setPresent(!present); return }
      if (/^[1-9]$/.test(key)) { const n = Number(key); if (n <= TOTAL_STEPS) { event.preventDefault(); setStep(n) } }
    }
    window.addEventListener('keydown', onKeyDown)              // window + bubble: after document capture (Radix Escape)
    return () => window.removeEventListener('keydown', onKeyDown) // and after document bubble (React handlers)
  }, [rootRef, step, setStep, present, setPresent, sectionNav])
}
```

```tsx
// snap-presentation.tsx — absolute scroll to a section's snap position (§4.3)
const pendingIndexRef = useRef<number | null>(null)
const scrollToIndex = useCallback((i: number) => {
  const scroller = scrollerRef.current
  const section = sectionRefs.current[i]            // registered by <SnapSection> via context
  if (!scroller || !section) return
  const padTop = Number.parseFloat(getComputedStyle(scroller).scrollPaddingTop) || 0
  pendingIndexRef.current = i
  scroller.scrollTo({ top: section.offsetTop - padTop })   // behavior 'auto' → follows motion-safe:scroll-smooth
}, [])
const next = () => scrollToIndex(Math.min(count - 1, (pendingIndexRef.current ?? activeIndex) + 1))
const prev = () => scrollToIndex(Math.max(0, (pendingIndexRef.current ?? activeIndex) - 1))
// reset pendingIndexRef to null when activeIndex catches up (useEffect on activeIndex).
```

Key placement: Prev/Next buttons `aria-keyshortcuts="ArrowLeft"` / `"ArrowRight"`; `StepNav` buttons `aria-keyshortcuts={String(step.stepNumber)}`; present toggle `"P"`; presentation region `"ArrowUp ArrowDown A Z"`; a `?`-opened help dialog lists everything. Keep `history: 'replace'` (nuqs default) unless Back-per-step is requested. Do not mount a second listener in `SnapPresentation`; it only exposes `scrollToIndex`/`activeIndex` through `PresentationContext`. `useToolbarShortcuts` should not be active on this route (it is toolbar-scoped today; verify no records toolbar renders inside the meeting flow, otherwise ←/→ would be claimed twice).

**Implementation notes (not research):** `getComputedStyle(...).scrollPaddingTop` is expected to return an absolute px value for `30cqh` (container units resolve at computed-value time); confirm once in DevTools at a `<lg` viewport. The `SnapSection` registry can be a `Map<number, HTMLElement>` in context, filled from `SnapSection`'s ref callback. If `present` lives in the URL, `useQueryStates({ step, present })` keeps both updates in one batched `replaceState`.

## Unverified

- `scrollIntoView` `container: 'nearest'` support: no entry in BCD `api/Element.json`; MDN only says "varying levels of support". Chromium's public tracker (issues.chromium.org) is JS-gated, so no Chromium bugs on smooth `scrollIntoView` + snap were reviewed.
- Firefox/WebKit "which scroller do arrow keys scroll" was not read from engine source; inferred from the WPT keyboard test (scroller focused → snaps) and Chromium's `LogicalScroll`.
- Screen-reader behaviour for a focused `role="region" tabIndex=-1` (browse vs focus mode) is asserted from ARIA 1.2's application-role text, not tested with NVDA/JAWS/VoiceOver; WebKit 251003 (VoiceOver + snap) is open.
- Firefox 1959811 (UNCONFIRMED) and WebKit 242566 (trackpad `scroll-snap-stop`) status beyond what the trackers show.
- Whether `getComputedStyle(scroller).scrollPaddingTop` returns px for `cqh` values in all three engines (spec expectation; not measured).
- Escape delivery to the page while the Fullscreen API is active (not researched; present mode as designed does not use the Fullscreen API).
- MDN marks `KeyboardEvent.repeat` "Baseline 2025 – Newly available"; the underlying reason was not checked.
